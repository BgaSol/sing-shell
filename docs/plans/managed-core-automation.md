# 核心自动安装与更新整改方案

状态：设计待实施。基于 `fd48fed` 的代码链路核对；本文不代表已实现行为，不修改当前 v0.2.0 的功能承诺。目标是首次无需寻找核心、日常无需维护版本，同时保持正在运行的代理稳定。应用自身仍手动下载、明确重启更新。

## 1. 验收行为与范围

| 场景 | 最终行为 |
| --- | --- |
| 新用户打开应用 | 默认应用管理核心；后台立即恢复本地材料，缺少核心时自动下载本机架构的官方稳定版，不等待前端挂载 |
| 下载期间导入配置 | 接受原文件路径，明确显示待核心校验；下载完成不自动启动 |
| 已有可用核心 | 后台检查、下载不阻塞使用现有版本；启动不等待发行网络 |
| 新版准备好且核心停止 | 校验当前配置后自动采用，不重启整个应用 |
| 核心正在运行 | 继续使用原进程，新版下次手动启动前生效；不自动断开、停止或重启 |
| 新版不兼容或启动明确失败 | 保留旧版；满足本方案的条件时只尝试一次回退，不循环重启 |
| 用户关闭自动更新 | 保持当前版本，允许明确的手动更新；首次安装和当前版本缺失后的恢复单独处理 |
| 用户采用外部核心 | 不自动下载、替换、清理或接管外部程序；路径失效也不擅自切为托管 |
| 应用退出或更新重启 | 取消后台维护、等待真实收尾、停止核心；下次打开不自动运行核心 |

只支持官方正式稳定版，不加入版本列表、测试版通道、定时重启、后台服务、系统代理、TUN 提权、订阅或配置自动迁移。不新增生产依赖，不改变五个原生系统架构目标和现有标准安装器。

“核心运行中”仍只表示进程状态，不代表节点、DNS、TUN 或互联网连通。核心的下载更新与应用的 updater 签名安装分开处理。

## 2. 已核对的现有链路及阻碍

| 入口和代码 | 当前事实 | 本轮需要调整的职责 |
| --- | --- | --- |
| [main.rs](../../src-tauri/src/main.rs) 的 setup、core_action、choose_file | 启动只拉起更新服务；IPC 直接调用 RuntimeService；文件框打开期间占 Selection 票据 | 后台维护从应用启动发起；核心用例通过唯一协调入口；文件框结果返回后才接纳变更 |
| [settings.rs](../../src-tauri/src/settings.rs) | engine 同时表达来源和已选版本；配置只有一个路径；偏好只有 automatic；所有写入使用一个 revision | 区分来源、受管版本记录、待校验配置和自动更新偏好；避免自动切换导致网络草稿反复冲突 |
| [runtime.rs](../../src-tauri/src/runtime.rs) 的 import/start | 没有核心就不能导入配置；启动重新读设置；spawn 成功立刻标记 running，随后 supervisor 才发现异常退出 | 用固定启动参数；支持待校验路径；增加有界启动结果，回退由协调层决定 |
| [updates/service.rs](../../src-tauri/src/updates/service.rs) 的 start/check | 应用与核心共用全量周期；全量检查跳过未托管核心；只发现、不自动下载 | 两个组件独立到期和失败重试；缺核心的首次安装不依赖应用检查开关 |
| 同文件 prepare/verify | 核心包准备与配置校验耦合；验证要求候选高于当前版本 | 分开包真实性、配置兼容、版本策略；恢复当前版本和回退不能沿用“只能更高”的规则 |
| 同文件 apply_engine | 直接保存新选择并显示 current；previous 只是调用中的临时变量 | 核心选择、上一版本和首次启动确认必须持久化；“已采用”与“上游最新”分开 |
| [updates/engine.rs](../../src-tauri/src/updates/engine.rs) | 已有摘要、架构、限额解包、实际版本检查；prepare/verify 自行读取设置；cleanup 只接收 current/previous | 复用校验能力；移除业务选择；保护准备中和待首次启动的版本；补齐解包/散列取消 |
| [app.rs](../../src-tauri/src/app.rs) 的 Admission | Runtime/Selection 串行，Check 与所有 Download 冲突；没有核心切换操作 | 按两条真实维护链路接纳；核心选择/启动/切换共享互斥边界，后台下载保持可并行 |
| [lifecycle.rs](../../src-tauri/src/lifecycle.rs) | 应用重启流程同时负责核心切换 | 核心采用退出该流程；生命周期仅负责停止收尾与应用安装 |
| [runtime.ts](../../src/runtime.ts)、[updates.ts](../../src/updates.ts)、[update-model.ts](../../src/update-model.ts) | 缺核心时禁用配置；两个组件都进入 ready() 和“重启并应用” | 首页展示自动准备；核心不计入应用待重启数；表单和日志保持局部刷新 |
| [测试支持层](../../src-tauri/tests/support/mod.rs)、[真实核心测试](../../src-tauri/tests/real_core.rs) | 生命周期测试绕过生产用例入口；受管测试直接写 settings.engine | 资源级测试保留；新增用生产协调服务驱动的完整链路，不能靠手工改选择来证明自动更新通过 |

不能在页面挂载时自动点击“检查/下载”，也不能在旧 apply_engine 外围增加一个定时调用。那样会继续继承配置导入、来源竞争、回退恢复及应用重启的耦合。

## 3. 目标职责与依赖方向

```text
Tauri setup ──> Application 后台维护入口
                    ├── CoreService ──> ManagedCore ──> 发行/传输/核心包校验
                    │       ├── SettingsStore
                    │       └── RuntimeService ──> platform / logs
                    └── UpdateService（仅应用更新）──> 官方 updater

首页/更新页 ──> IPC ──> CoreService 或 UpdateService
退出/应用升级 ──> Lifecycle ──> 封闭接纳、等待任务、停止核心、应用安装
```

具体调整如下，保留现有标准库和 Tauri/Tokio 能力：

| 文件/模块 | 唯一职责与改动 |
| --- | --- |
| 新增 `src-tauri/src/core/mod.rs` | CoreService：配置选择、核心来源、启动/停止、采用准备版本、首次启动确认与一次回退；是受管选择的唯一写入者 |
| 新增 `src-tauri/src/core/managed.rs` | ManagedCore：核心候选、独立维护周期、下载准备、缓存与失败状态；返回已准备的包，不修改 active/previous，不启动代理 |
| 将 `updates/engine.rs` 的专用逻辑迁入 `core/package.rs` | 核对归档/程序、解包、原生架构、版本和安全清理；输入显式路径和取消标记，不读取当前配置或决定来源 |
| `runtime.rs` | 临时检查进程和唯一运行进程的所有权、日志、启动观察及退出结果；不保存用户设置、不发起下载、不选择回退版本 |
| `settings.rs` | 唯一持久化写入者；提供针对核心上下文与偏好的串行局部提交，保存时从最新状态合并对应字段 |
| `updates/service.rs` | 缩减为应用候选、签名下载和安装缓存；删除核心 active 切换和全组件混合周期 |
| `updates/release.rs`、`updates/network.rs` | 继续共用已有的两种具体发行适配和传输；增加按明确核心版本解析资产的入口供修复使用，不做通用发行框架 |
| `app.rs` | 组合服务和接纳；一个后台唤醒循环分别触发应用检查与核心维护，不等待某条网络任务完成才启动另一条 |
| `main.rs`、`lib.rs` | 装配、模块导出、原生文件选择和类型明确的 IPC；不在命令函数中组织核心升级步骤 |
| `lifecycle.rs` | 正常退出、普通重启和应用升级的统一收尾；不再调用 apply_engine |

散列等已有能力保留单个实际实现供应用/核心文件核对复用；移动调用位置时同步测试和夹具。不增加 Service trait 层、仓储层、插件注册、工作流解释器或第二套异步运行时。CoreService 不反向依赖应用更新服务，应用更新服务也不持有 CoreService。

后台入口调用 CoreService 的维护用例，由它消费 ManagedCore 的准备结果；ManagedCore 不保存指向 CoreService 的引用。CoreFetch 完成后先释放维护票据，再独立尝试获取核心变更票据采用，避免递归接纳和服务循环依赖。关键阶段使用具体枚举和错误类型，序列化给前端时映射展示，不用散落的字符串分支决定回退和重试。

## 4. 设置、候选与恢复记录

设置升级为 schema 2，在原 `settings.json` 中保存用户选择和恢复所需事实，不新增数据库或第二份 active 指针。

| 数据 | 内容与约束 |
| --- | --- |
| `coreSource` | `managed` 或 `external {path}`。新安装默认为 managed；“未安装”由受管 active 为空表示 |
| `managed.active` | 当前受管程序引用：版本、本机 target、程序 SHA-256 与来源证据；文件路径由数据根目录推导 |
| `managed.previous` | 至多一个上一可回退引用；回退前仍要复验程序与当前配置，不能把“文件还在”当作可用 |
| `managed.trial` | 当前采用版本的首次启动状态：`awaitingStart` 或 `starting`，绑定 active 身份；不是通用安装事务日志 |
| `managed.blocked` | 至多一个失败候选身份、失败阶段和原因。阻止自动反复采用同一坏候选；不是历史版本黑名单 |
| `configPath` | 最近一次成功通过所选核心检查的配置路径；每次启动仍重验 |
| `pendingConfigPath` | 没有核心可用时用户先选的路径；不是有效配置承诺，不覆盖已有 configPath |
| `updatePreferences.automatic` | 保留为应用自动检查开关，不扩大为应用自动下载安装 |
| `updatePreferences.automaticCore` | 核心自动检查、下载和安全采用，默认开启 |
| `coreRevision` / `preferencesRevision` | 两个明确修订域。核心切换不令网络草稿冲突；偏好保存不覆盖后台刚提交的核心选择 |

程序引用中的新下载证据绑定版本、target、官方 tag、asset ID、归档摘要和展开程序摘要。同版本不同资产身份不得静默覆盖；普通准备遇到已有版本目录与预期不一致时失败，不原地覆写可能运行的程序。同版本修复是明确的独立分支，按第 5 节执行。

核心准备记录沿用 `updates/engine/prepared.json`，升级为专用格式，绑定包身份、程序摘要以及自动/明确手动请求来源。核心的候选和 nextCheckAt/nextRetryAt 保存在该组件自己的缓存状态中；应用继续使用自身缓存。进度、PID、在途任务与 compatibility 结论不作为可信持久事实。

偏好表单使用 preferencesRevision。CoreService 的长校验使用 coreRevision 检查上下文是否变化；在途下载另带操作 ID 与来源代次。网络配置变化只使旧线路健康结果失效，不把已通过摘要校验的下载变成坏包。原单一 revision 迁移为这两个具体修订，不维护第三套总修订；网络已有 revision/epoch 仅用于传输快照与线路健康隔离。

迁移规则必须一次定义并测试：

- 无设置：schema 2、managed、active 为空、automaticCore=true；缺核心自动安装。
- v0.1.0 的 corePath 或 schema 1 external：保留外部来源和配置路径，不开始托管维护，不根据路径是否位于应用目录来猜测归属。
- schema 1 managed：保留当前版本；automaticCore 继承旧 automatic，尊重原来已关闭检查的用户。旧设置没有上一版本记录，不能扫描目录后猜一个 previous。
- schema 1 engine 为空：转为 managed 且 active 为空；首次安装独立于后续更新开关。
- 旧受管程序缺少官方来源记录：显式标记为 legacy，不把对现有文件重新计算的散列说成官方真实性证明。恢复时先按旧行为核对本机架构/实际版本，建立本地变更检测基线；后续新下载必须具备完整上游证据。旧文件不合法就进入恢复，不直接执行。
- v0.2.0 的应用签名缓存不因核心整改而丢弃。旧核心准备记录仅在真实字节复验后转换；外部来源下即使有 ready 缓存也不得自动接管。
- 原文件按输入 schema 保留备份后原子替换；损坏、未知版本、备份/保存失败均保留原件并禁用自动维护和设置覆盖。迁移不联网、不启动代理，不在打开设置文件时执行所选外部程序。

schema 2 不承诺旧应用能读取。回装旧应用需要恢复对应备份；新应用不得以覆盖设置的方式掩盖降级失败。

## 5. 后台维护、首次安装与重试

Application 在 setup 后启动一次后台服务；本地缓存恢复不依赖首页。应用与核心各有状态、到期时间及失败原因，只共享一个轻量定时/唤醒入口。使用现有 Tokio 时间和 Notify；正常每分钟判断，下载完成、停止、配置/来源/偏好变更时唤醒，事件只要求重新读事实。

核心维护顺序固定为：

1. 本地恢复与字节核对。
2. 当前来源是否 managed、设置是否可写、是否关闭中、是否已有核心维护任务。
3. 无任何已选受管核心时走首次安装；有引用但程序丢失/损坏时走当前版本恢复；其余按自动更新开关和周期判断。
4. 发现候选 → 固定身份 → 下载前复查 → 下载/摘要验证 → 有界解包/原生架构/实际版本验证 → 提交准备记录。
5. 通知 CoreService 尝试安全采用；不能采用时保留准备结果，不能在下载 worker 中直接改当前选择。

首次安装在本地恢复后立即开始，不等旧的 10 秒应用检查延迟。普通核心更新成功或无新版后约 24 小时再检查；临时网络失败约 15 分钟后重试。应用仍保留自己的检查节奏，应用失败不推迟核心，手动检查不重置另一组件的周期。

失败按阶段处理，不按中文错误字符串猜：网络/限流可以有界重试；摘要、资产身份、架构、解包、实际版本错误或配置不兼容，不每 15 分钟反复下载相同候选。记住一个 blocked 身份，遇到新身份、用户明确重试或配置重新校验时再处理。用户手动重试前后仍核对官方资产，不能绕过验证。

同一版本的资产身份变化意味着来源发生变化，不能因“出现新身份”就自动解除阻止并覆盖版本目录；需明确手动重试并重新核验。配置不兼容只保留正确程序和兼容错误，不给所有网络/配置错误统一打永久禁用标签。磁盘写入/空间不足在本会话暂停自动写入，用户处理后可重试；不能转成每分钟反复写盘。

取消只停止当前维护任务，并抑制本次应用会话自动重新发起；手动重试或下次打开应用可以恢复。已有核心时关闭自动更新会取消自动来源的任务，并禁止尚未进入提交的自动采用；明确手动发起的更新仍按该次请求完成。已准备的自动候选可以保留，不能在开关关闭后偷偷于下次启动采用。

首次安装是获取运行所需文件；关闭“自动更新核心”不阻止它。已选版本损坏时先尝试有效本地 previous，或恢复绑定的同版本官方资产，不因修复而自动升级到另一版本；资产身份变化时明确失败，用户可手动更新。此规则也适用于关闭后续自动更新的情况。

同版本修复先把可信资产展开到新 staging 并完整校验。只有核心已停止、全部资源收尾、来源仍为 managed、待修复文件确实缺失/损坏且记录仍匹配时，才在核心变更票据内原子替换受管程序；写入前后中断只会留下旧损坏文件或新完整文件，下次据摘要恢复，不以 `.part` 冒充完成。有效程序和运行中的文件不能走这个覆盖分支。legacy 没有固定资产证据时先按精确版本取得官方源证据，不猜缓存包；该源不可用则提示手动处理。

生产只从官方 GitHub HTTPS API 获取 sing-box 资产摘要，包字节可以复用已有备用线路。无凭据、API 不可达时明确失败，不以镜像提供的摘要作为唯一依据。首次本机没有可用网络时，保留配置路径，提示联网重试或选本机核心，不加入代理自举服务。

## 6. 配置导入与核心采用

配置选择由 CoreService 负责，RuntimeService 只执行检查。两种导入行为必须保持一致的失败边界：

- 有可用核心：继续用当前核心校验，通过才替换 configPath；错误不丢失此前有效选择。
- 无可用核心：核对绝对路径、文件类型与可读性后保存 pendingConfigPath，显示“等待核心校验”。不自行解析 JSONC，不宣称配置有效。再选另一文件时仅替换 pending，不改写文件正文。

首次核心包验证通过后，先采用可执行程序，再检查 pendingConfigPath；配置失败单独显示，不把它当成核心下载失败，也不反复下载同一核心。通过后在一次局部提交中提升为 configPath 并清除 pending。文件失效时保留可解释的错误，允许重新选择。

正常升级把“包正确”和“配置兼容”分开：包准备好不等于可立即替换当前版本。用候选执行当前配置检查；失败则旧选择不变，保留已下载材料供本地重试。配置被修改或导入新路径后重新检查，不复用旧 compatibility 标记。

后台兼容检查可基于只读上下文执行，不占用核心变更票据。提交采用前短暂获取核心变更票据，并重新确认 coreRevision、来源代次、当前进程已停止、当前自动/手动策略与候选身份；上下文变了就保留 ready 并重新核对，不以旧结果写入新选择。

最终来源、coreRevision 与 automaticCore 条件由 SettingsStore 在同一次串行局部提交内再检查，与偏好保存确定先后顺序，不能在锁外检查开关、随后无条件写 active。用户修改原文件不能被设置修订识别，因此候选检查后还要核对主配置路径/字节是否变化；资源引用的完整语义仍由每次 sing-box check 保证。此轮不加文件监视器：导入、明确校验/重试和启动会重新检查；后台定时不重复运行同一份不兼容配置。

安全采用只有这些触发点：准备完成、用户正常停止完成、启动时本地预检、明确切回应用管理。运行中与停止收尾未完成时均不切换；异常退出不会触发自动重启，候选留到下次手动启动再处理。

采用时一次保存 previous、active、trial=awaitingStart。previous 仍需是可复验的旧引用；当前 active 尚在首次启动确认阶段时不连续采用下一个版本，避免覆盖回退点。准备记录最后提交、选择记录先于缓存清理；设置写失败时选择保持原状。

当前 active 仍有 trial 时暂缓自动获取下一版本，直到首次启动确认或回退完成；不堆积升级队列。后台采用若已占有核心变更票据，用户启动只可能等待有界的本地提交/复核，不等待发行网络或下载。采用旧记录重试时如 active 已等于候选，按幂等成功收尾，不能再次旋转 previous。

“使用应用管理核心”从外部来源切回时：若有有效本地受管版本可验证后提交；否则仅创建一次明确的准备请求，在核心和当前配置可用前保留外部选择。请求期间再次选外部核心使该请求失效。退出后若仍是 external，缓存本身不能代替用户的接管意图。

配置检查可能按 sing-box 的行为读取远程规则等资源。壳在本地采用/启动阶段不发更新网络请求，但不能承诺任意用户配置都能离线通过 check；超时/失败时保留当前版本和原因，不删改规则或配置来强行通过。

## 7. 启动确认、一次回退与崩溃恢复

CoreService 的 start 不调用发现或下载。只有本地已准备候选可以在本次启动前采用；还在下载就启动当前可用版本。完全没有核心时返回“核心正在准备/请重试”，不保存一个稍后自动执行的启动请求。

RuntimeService 接收不可变 StartSpec（程序引用、程序路径、配置路径、工作目录、操作 ID），避免分步骤重新读取变动后的设置。supervisor 始终独占运行 Child；启动调用等待 supervisor 的有界结果，不让两个线程同时 wait/kill 同一个进程。

程序创建后进入 starting。完成校验并存活 2 秒后才确认本次启动；期间异常退出必须带退出状态和资源收尾结果。2 秒仅用于捕捉明显启动失败，不是网络健康探测；之后异常退出继续沿用原行为，显示错误且不自动重启。

一次回退只适用于新采用、尚未确认首次启动的受管核心：

1. 启动前将 trial 写为 starting。记录失败时不创建新进程。
2. 新版在校验/创建进程/启动观察中明确失败时，先确认新进程、进程组和日志 reader 已结束。
3. 若有 previous，重新核对其文件、架构、实际版本与同一份当前配置；通过后一次保存回退选择及 blocked 候选。
4. 仅在用户本次仍希望启动、没有取消或关闭的情况下启动 previous 一次。
5. previous 也失败就保留两个阶段的原因并停止；不存在 previous 时保留失败事实。不能把旧版失败触发成新一轮更新或再次回退。

回退提交将旧 previous 提升为 active、清空 previous 和 trial；失败候选由 blocked 与准备槽记录，不能再把它当成可回退版本。恢复 prepared 缓存同样先核对 blocked、来源及开关，不能在应用重开后复活已经拒绝的自动采用请求。

用户主动停止、退出、取消、来源切换不算新版缺陷，不触发回退运行。外部核心不参与自动回退；无法确认资源收尾时也不启动旧版。端口冲突等早期失败可以触发一次旧版尝试，但界面只能报告实际失败，不能断言是新版程序缺陷；网站打不开或后期网络断开不触发回退。

主动停止/取消已确认收尾后，将尚未完成的 starting 恢复为 awaitingStart，再释放启动票据；避免正常退出被下次恢复误认为崩溃。若该记录保存也失败，明确报告恢复状态不确定，不能假装已经撤销。来源切换后清除不属于该选择的 trial，保留磁盘程序供以后明确切回，不创建自动接管意图。

trial 的恢复规则保持有限：

| 持久状态 | 下次打开行为 |
| --- | --- |
| awaitingStart | 本地重验 active，继续等用户启动，不因为尚未启动就回退 |
| starting 且未写入确认 | 视为启动结果不确定；优先恢复可复验的 previous 选择并提示上次启动未完成，不自动启动、不自动重试候选 |
| starting 且没有有效 previous | 显示待人工重试，保留程序/配置，不无条件重试或联网替换 |
| 启动已确认 | 清除 trial；普通后期异常退出不自动回退 |

启动确认保存失败时不得宣称恢复记录已完成；先停止本次进程并报告，停止失败则保留真实 PID/状态，禁止继续回退或安装。进程实际身份和持久选择不同步时必须明确显示，不用预期版本覆盖真实运行版本。

清理只在相应任务空闲后执行，保护 active、previous、准备候选、首次启动引用和在途 staging。正常最多保留当前、上一版、一个准备候选；失败候选材料由同一准备槽管理。清理失败只记日志，不撤销有效选择，不碰外部程序或用户配置。路径必须由受管根目录推导，拒绝越界和链接，不按任意 UI 路径删除文件。

## 8. 接纳、取消与提交边界

不增加一把覆盖网络、解包、进程和磁盘的全局大锁。延续现有 Admission 的具体票据，调整为以下真实互斥关系：

| 操作 | 接纳规则 |
| --- | --- |
| 核心发现→下载→准备 | 一个 CoreFetch 票据贯穿全链路；手动和自动共用，不用 Check 票据里嵌套申请 Download |
| 应用检查/下载 | 应用自己的票据；可与核心维护并行，一个组件至多一项，不复制全局 checking |
| 选择来源、配置提交、启动、采用、回退 | 共用核心变更票据；失败和取消也由原所有者收尾，不能让其他入口直接改选择 |
| 偏好保存 | 独立偏好修订与串行写入，不占核心变更票据；成功后唤醒维护入口 |
| 状态/日志读取 | 只读，不等待网络或进程操作完成 |
| 网络诊断 | 保留单个有界诊断；不占用核心启动票据 |
| 停止启动中的进程 | 向当前启动票据发取消，等待它回收，再完成停止；不另开第二个竞争 Child 的 stop worker |

原生文件框打开时不持核心变更票据。只限制同类文件框重复打开；结果返回后检查关闭状态和请求代次，再接纳校验/写入。应用已退出或选择已被更新时结果作废，不靠等待用户关闭系统文件框才能完成后台收尾。

下载回调必须核对操作 ID，来源变更使旧核心任务取消且不能采用其结果。偏好和网络配置用接纳时快照；保存新线路后旧任务不得污染新线路健康状态。配置变化可以保留正确包字节，但旧兼容结论失效。

散列、解包、复制和核心校验都接受同一取消标记，在循环/条目边界检查；沿用已有大小限额和命令/读取期限。取消不等于任务结束，票据必须等进程、reader、临时文件真实收尾后释放。

退出先封闭新操作并取消维护，再等待所有者，最后停止核心。已进入的原子设置提交允许完整结束；尚未进入提交的自动采用取消。超时保留错误与实际状态，不能假称已关闭。应用更新重启也取消后台核心维护并等待，不要求用户反复撞上自动下载的忙碌窗口；停止失败不调用安装器。

应用更新仅安装应用，不顺带处理核心 ready。重启后的核心本地恢复/安全采用仍按自己的来源和开关执行；普通启动和应用升级重启都不自动运行代理。

## 9. IPC 与前端交互

前端不拥有定时器维护任务、版本切换策略或回退策略。保持现有原生 DOM/Vite 与两页结构，不引入 UI 框架。

IPC 按具体对象拆清：

- core_snapshot 增加来源、安装版本、真实运行版本、核心维护进度、pending 配置、trial/回退提示及 canStart/canStop/canImport/canRetry 等操作可用事实。
- core_action 使用强类型操作，start/stop/check 转给 CoreService；增加核心检查、明确更新、重试、取消入口，手动维护和自动维护走同一条后端用例。
- choose_file 仍负责系统文件框，返回路径只交 CoreService；切回托管通过明确的来源选择命令，不让 UI 提交任意受管安装路径/版本。
- 应用 check/download/cancel/snapshot 保留自己的命令；request_restart 不再接收 App/Engine 组合，核心请求不能落到应用安装器。
- 偏好保存增加 automaticCore 并改用 preferencesRevision。镜像与诊断复用现有入口；核心下载状态回调不能因自动切换刷新表单草稿。

首页核心区域默认显示“应用管理”，展示当前版本和必要的准备/失败提示；本机程序选择放在可展开的高级选项。无核心时导入按钮可用，启动按钮说明正在准备；有核心时下载不让启动和日志一起进入 busy。每个操作可用事实由后端最终复验，不把按钮禁用当成接纳保护。

核心卡片至少区分：正在查找/下载、等待配置校验、已就绪、新版待下次启动、更新失败但当前版可用、已回退、外部手动管理。不要用一个全局 error 掩盖可用核心，也不要把采用成功写成“上游已是最新”。

更新页仍展示两项，但应用只显示应用重启入口，核心显示自动维护、手动检查/更新与重试/取消。“下载可用更新”若保留，应只针对应用；不得继续把 ready(engine) 计入待重启数或一起提交 request_restart。

“自动更新核心”保存后生效；应用的每日检查开关语义保持独立。关闭后对自动来源 ready 显示“已暂停自动采用”，用户明确点“更新核心”才继续。普通检查与成功维护不弹系统通知；失败给本地可操作提示和日志。

快照刷新只更新固定节点，不重建网络表单、详情和日志容器。首页核心状态只读一份 CoreSnapshot；运行版本来自运行进程的身份，停止后的默认版本来自 active。进度、配置错误和应用更新错误分属各自区域。后台核心切换不造成偏好 revision 冲突；真正的偏好并发编辑仍保留输入并提示载入最新值。

## 10. 测试与原生验收

先将当前入口能复现的缺口固化为失败测试，再移动职责和实现；不得只给纯决策函数加测试就认为整条链路通过。

| 链路 | 必须覆盖的场景和证据 |
| --- | --- |
| 设置与迁移 | 无设置、v0/v1 外部/v1 受管、旧关闭开关、损坏/未知 schema、备份/提交失败；核心与偏好并发保存互不覆盖；迁移两次无副作用 |
| 无核心首次使用 | 无前端自动开始；可先保存 pending 配置；下载正确后采用、校验配置且不启动；配置错误不造成重下核心；断网可重试 |
| 调度 | 独立应用/核心周期；首次立即、24 小时、15 分钟；开关、手动单项、睡眠恢复、取消会话抑制；应用失败不饿死核心任务 |
| 下载和缓存 | 沿用网络回归；缺摘要、身份变化、错架构、路径穿越/链接、过量归档、慢响应/取消；只有 part、记录缺失、ready 后篡改、断网重开、当前版本恢复 |
| 来源与配置竞争 | 下载中改选外部；打开文件框期间退出；配置导入/原文件修改与准备完成同时发生；旧进度/旧错误不能覆盖新操作 |
| 安全采用 | 运行中准备新版，真实 PID 和 SOCKS5 流保持；停止 reader 未收尾不切；停止后采用不重启壳；正在启动时不切；有旧版且下载未完直接启动旧版 |
| 首次启动与回退 | spawn 后立即退出、观察窗内退出、观察窗后退出、取消/退出、回退也失败、无 previous、持久化失败、进程清理失败；最多一次回退并保留真实版本 |
| 崩溃恢复 | staging 后、prepared 后、active 提交前后、trial=starting 后、确认前后中断；重开不自动启动，不猜目录、不反复采用坏候选、不删唯一可用版本 |
| 用户关闭自动更新 | 无新的自动下载；在途自动任务取消；已有自动 ready 不在启动时偷偷采用；明确手动更新仍可进行；首次安装/同版本修复按约定执行 |
| 外部核心 | 新老设置都不接管；路径失效明确报错；切托管失败保留旧选择；所有步骤前后比较外部程序与配置字节 |
| 前端 | 配置待校验与下载并存；有核心下载时能启动；启动中可停止；日志/输入/选区/滚动稳定；核心不计应用重启数；偏好草稿不被自动切换冲掉 |
| 应用更新回归 | 独立签名、公钥及正式源不变；核心维护中应用重启能够收尾；应用安装失败不虚报核心成功；旧版设置迁移后正常使用 |

测试工具保持具体：调度通过显式 now 参数与现有 Tokio 测试能力控制，不真实等待一天；test-fixtures 提供两个不同正式版本、可延迟/失败的本机核心夹具。版本、网络测试源和安装路径注入仅在测试构建内开放，不给生产客户端新增任意 endpoint、公钥或下载后脚本入口。

`tests/support` 增加 CoreService 驱动方式；RuntimeService 的进程资源测试仍可单独保留。受管真实测试从“直接写 engine 后启动”改为“接纳准备→验证→采用→启动→停止”，并增加运行中准备新版不打断 SOCKS5 往返的集成测试。

真实上游测试使用明确固定版本/摘要的官方归档；回退故障用可控夹具，不篡改真实包后冒充官方新版本。正式包验收区分“安装包内程序 smoke/IPC”和“同源核心服务集成”，报告按实际范围填写，不能把 helper 的通过说成所有真实用户配置已验证。

相关实施步骤运行 `npm run check`、`npm run scripts:test`、`npm run test`、`npm run build`。正式交付仍在 Windows x86_64/ARM64、Linux x86_64/ARM64、macOS ARM64 上原生执行实际包启动/退出、官方核心和应用 updater 验收；ARM64 不能以交叉编译代替。

扩展 `scripts/verify-package.mjs`、`scripts/smoke.mjs`、`tests/fixtures/upgrade.rs` 对 schema 2 的断言：保留来源、配置、核心自动更新开关和受管恢复字段；保留 v0.2.0/schema 1 到新版的升级样本，另外测新版基线到高版本候选。生产 smoke 禁止互联网维护，测试使用独立数据目录，不操作桌面或用户真实代理。原包 Artifact 复用、独立 verify、metadata 在 package 被跳过时仍执行的回归继续保留。

## 11. 实施顺序与完成条件

每步是可验收的完整主题，同步相应调用者和测试；允许步骤间调整私有函数，不保留新旧两套生产入口长期并行。

| 步骤 | 代码及配套 | 完成条件 |
| --- | --- | --- |
| A：核心用例边界 | CoreService、Runtime StartSpec/结果、Admission、main/lib、测试支持层；复用现有手动下载功能 | 所有来源/配置/启动入口经过协调服务；现有流程不退化；低层不自行保存选择 |
| B：状态与首次安装 | schema 2、双修订、ManagedCore、核心包职责拆分、pending 配置及首页最小状态 | 干净目录无需选核心，能先导入配置；首次安装与失败重试闭环；旧 external 不变 |
| C：后台更新与本地采用 | 单维护入口、独立周期、操作/来源代次、兼容检查、安全采用；移除核心依赖应用重启 | 下载期间旧核心可运行；停止后/下次启动前采用；关闭自动更新及取消真实生效 |
| D：启动回退与恢复 | previous/trial/blocked、2 秒启动观察、一次回退、缓存清理及退出竞争 | 失败有确定结果，恢复不循环启动、不丢选择；故障注入和资源释放回归通过 |
