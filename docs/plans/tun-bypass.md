# 自定义直连规则的 TUN 绕过：功能与代码整改方案

状态：功能范围已确认；代码整改方案已补充，尚未实施。第 1–10 节定义功能合同，第 11–18 节说明完整链路、局部重构、验证顺序与实施门槛。

## 1. 目标与最小范围

用户在已有的自定义直连规则中勾选“绕过 TUN”，让指定目标直接使用系统网络，减少 TUN 转发对远程控制、打洞等连接的干扰。用户沿用已有的域名与 IP，无需声明 RustDesk、选择程序文件或编辑核心配置。

首版支持精确域名、IPv4 / IPv6 地址及 CIDR。域名在每次连接准备时解析，当前会话固定使用本次结果，重新连接时刷新。此范围已由用户确认。

功能只承诺指定地址按约定绕过 TUN。它不判断流量属于哪个程序，也不承诺 RustDesk 在任意 NAT、防火墙或网络环境下都能打洞成功。

## 2. 入口与操作

在“分流 → 新建 / 编辑自定义规则”的“统一出口”下方增加一个复选框：

> □ 绕过 TUN
>
> 这些目标直接使用系统网络，可改善远程控制和打洞兼容性。按目标 IP 生效，优先于其他分流规则；访问相同 IP 的其他服务也会绕过。

复用当前编辑弹窗、域名列表、IP 输入、完成、保存规则和应用并重连，不新增设置页面、应用识别流程或二次确认弹窗。复选框可通过键盘操作，说明与控件关联；错误就近展示并保留输入。沿用现有紧凑布局和最小窗口要求。

| 场景 | 行为 |
| --- | --- |
| 自定义规则，出口为直连 | 显示“绕过 TUN”，新旧规则均默认不勾选 |
| 自定义规则，出口为代理 | 不提供可启用的绕过选项 |
| 从直连切换为代理 | 在当前草稿清除绕过，并提示“切换为代理后已关闭绕过 TUN”；切回直连不自动重新勾选 |
| 包含“包含子域名”的条件 | 保留原匹配方式，绕过不可勾选，旁边说明“绕过 TUN 仅支持精确域名，请先修改匹配方式” |
| 已勾选绕过后改为“包含子域名” | 阻止完成并定位该域名；用户改回精确匹配或取消绕过，不自动改变用户选择 |
| 固定开源来源、默认规则 | 不提供绕过选项 |
| 整条规则禁用 | 保留绕过偏好，本次不生成任何排除；重新启用后恢复该偏好 |
| 原始配置模式 | 沿用现有分流不可用状态，不注入此功能 |

一条规则只有一个绕过选项，作用于该规则内全部有效域名和 IP。需要部分绕过时，沿用现有能力拆为两条规则，不增加逐项开关。

规则列表在该规则出口旁显示“直连 · 绕过 TUN”；禁用规则明确显示已关闭。列表展示的是已保存或正在编辑的配置，是否已经运行仍由现有“待应用”状态表达，不把勾选显示成已经生效。

## 3. 地址与 DNS 行为

### IP 与网段

直接使用现有输入和规范化结果。用户填写单个 IP 时按单地址处理，填写网段时作用于整个网段。不把其他直连规则、国内 IP 来源或默认直连自动加入排除集合。

继续执行现有地址校验。绕过目标还不得与本应用 TUN 地址段、隧道 DNS 地址或 Fake-IP 保留池相交；默认路由也不能作为绕过目标。错误指出规则与具体条目，不静默裁剪、缩小网段或跳过条目。解析得到的地址执行同样检查。

### 精确域名

1. “完成”和“保存规则”只做本地校验，不依赖 DNS 或服务器在线；用户可以离线编辑。
2. 连接、应用并重连、切换节点及应用启动后的新连接准备，均通过物理网络解析这些精确域名，收集可用的真实 A / AAAA 地址。
3. 去重后的结果与手填 IP / 网段共同构成本次排除范围。域名至少有一种地址族的有效结果即可；没有另一种地址族的记录属于正常情况。
4. 当前会话内，这些精确域名经应用管理的 DNS 查询得到的真实地址，必须与本次确认的排除范围一致，不返回 Fake-IP，也不在后台换成一批未排除的地址。HTTPS / SVCB 查询成功返回空回答，避免额外的地址提示绕开固定结果；其他查询类型保持原有直连解析。只固定绕过域名的地址回答，不冻结普通域名的 DNS。
5. 本次会话不随 DNS TTL 动态改路由。地址变更后，用户使用已有“应用并重连”重新解析，不新增刷新按钮、定时器或自动重连。

域名解析、结果数量和连接准备必须有界；超时、结果超限、无可用地址或地址冲突都使本次准备失败，显示规则名、域名和可执行的下一步。禁止只应用成功的一部分，或悄悄退回普通直连。具体内部额度在代码方案中结合既有规则与授权消息上限确定，不增加用户可调参数。

应用不能控制第三方 DoH / DoT、程序内部地址缓存或另一个 VPN。它们使用本次排除范围以外的 IP 时，仍按现有 TUN 与分流规则处理；不为追踪这些地址新增监听或抓包。

## 4. 优先级与明确边界

绕过在系统路由层先于核心分流生效，是用户明确启用的例外。只有进入 TUN 的流量，才继续遵循现有有序策略表与默认出口。现有分流“全部按列表顺序首次匹配”的说明，需要同步注明这个例外。

- 普通规则无论排在前面还是后面，都不能把已经排除的真实目标 IP 再送入代理。
- 绕过规则仍留在原列表位置，不新增另一张规则表；拖动不改变其系统排除优先级。关闭绕过后，该规则恢复所在位置的普通分流行为。
- 域名解析得到的 IP 按整个目标地址排除，不限端口、协议或程序。共享 IP 上的其他域名和服务也受影响；不会声称“只绕过这个域名”。
- 规则重叠时，已排除的真实地址按绕过处理。不为了保留普通规则顺序而推算域名与 IP 的差集、展开固定来源或实现第二套匹配引擎。
- 其他域名即使恰好与绕过目标共用真实 IP，也不因此自动改变其 DNS 策略；若仍得到 Fake-IP 并进入 TUN，继续按核心规则处理。不能承诺共享 IP 上所有访问方式表现完全相同。
- 绕过流量交给系统网络，既有 VPN、防火墙和接口路由仍可能影响它；“绕过 TUN”不等同于保证物理直出或公网可达。
- 核心的 IPv4 兼容模式只约束进入 TUN 的流量。绕过目标使用系统网络的 IPv4 / IPv6，旁路流量不受该模式的 IPv6 拒绝约束。精确绕过域名的真实地址回答也遵循这一边界；相关功能说明同步明确，不新增开关。

## 5. 保存、应用与清理

沿用“页面草稿 → 保存规则 → 应用并重连”的流程：

- 修改后不自动重启、提权或改变当前网络。未连接时下次连接采用；正在运行时保存后显示待应用。
- 开关、域名和 IP 均属于同一条规则的连接意图。关闭、删除规则或切换到代理，成功应用后撤销对应排除。
- 候选连接先完成全部解析与校验，再替换当前连接。准备失败时，现有连接及其已确认的排除范围保持不变，新设置保留待应用状态。
- 切换失败如触发现有的一次恢复，恢复旧连接时必须使用旧连接实际采用的目标集合，不能混入新解析结果；新建连接则重新解析。用户不需要管理这个运行快照。
- 普通停止、退出和核心异常结束，按现有资源所有权释放本次排除，不留下持久系统路由或新增常驻服务。清理失败沿用现有阻止新连接和重试机制。
- 受控连接的就绪检查必须识别“本次明确排除”与“本应接管但缺失的路由”，不能为了支持排除而放松其他目标的覆盖检查。尚未就绪时不显示已连接。

旧设置缺少此选项时按关闭处理，保留节点、凭据、现有规则与排序，不要求重新初始化或重新导入。切换节点沿用已保存的绕过选择。

## 7. RustDesk 使用示例

用户已有一条自定义“RustDesk”直连规则：

1. 若使用域名，将 ID 服务地址设为精确匹配；也可以沿用已有服务器 IP。
2. 勾选“绕过 TUN”，完成并保存规则，点击“应用并重连”。
3. 重新发起 RustDesk 会话，检查它实际显示的是直接连接还是中转。

ID 与中转共用 IP 时可复用同一项。两者分开部署时，只有中转地址的旧规则不能覆盖 ID 服务；用户需要补上 ID 地址。应用不自动读取 RustDesk 私有配置，也不自动发现被控端动态公网地址。

若仍然走中转，不继续扩大排除为所有直连目标，也不显示“打洞已修复”。此时需要根据 RustDesk 的连接结果另行诊断。

## 9. 复杂度约束

首版只新增一个规则级偏好，以及实现其所必需的解析结果与会话生命周期处理。不增加应用名单、进程绕过、服务发现、子域名抓取、DNS 后台刷新、独立刷新按钮、系统代理模式、自动重连、测速、通用路由编辑器或生产依赖。原始配置与外部核心继续由用户维护。

代码整改必须同时落实：现有规则与运行输入的兼容、精确域名真实回答与排除集合的一致性、有界准备与取消、授权边界、三类操作系统的路由就绪及回收、失败恢复和对应回归。若当前官方核心不能可靠实现其中任何行为，应明确指出限制并调整方案，不能通过静默降级交付。

实现通过后，将最终行为迁入分流、核心和活动功能文档，并同步开发验证说明；删除本计划，不保留完成归档。

## 10. 依据与证据强度

- Mihomo / Clash 的公开反馈使用服务端 IP 路由排除，并在 Fake-IP 模式让域名真实解析；有后续用户确认可用：[讨论与配置](https://github.com/rustdesk/rustdesk-server/issues/457#issuecomment-2399399702)。这是方案依据，不能视为本应用或本次 P2P 已验证。
- [sing-box 的 TUN 参数](https://sing-box.sagernet.org/configuration/inbound/tun/#route_exclude_address)提供地址排除能力。参数存在不代表平台生命周期与上述全部行为已经通过验证。
- 当前应用使用 mixed 协议栈、默认 TUN、固定运行输入、显式应用重连和按需授权 worker；方案沿用这些边界。

## 11. 已追踪的代码链路与问题

本方案基于当前源码追踪，以下均是本功能必须经过的入口，不只修改配置生成器。

| 链路 | 当前代码 | 整改原因 |
| --- | --- | --- |
| 编辑与保存 | src/routing.ts → routing_validate / profile_set_routing → profile/service.rs → SettingsStore::routing | 编辑弹窗与列表都能切换出口，必须共用关闭绕过的行为；保存继续保持无 DNS、无网络副作用 |
| 规则校验 | profile/routing.rs 的 Policy、Routing::normalized | 统一约束“自定义、直连、精确域名”，不能仅靠前端禁用控件 |
| 连接意图 | profile/connection.rs、SessionService::connection_for / execute_connection | ConnectionInput 同时用于待应用比较、授权请求、最后成功连接；不能把每次解析的 IP 塞进去造成设置抖动或恢复旧 DNS |
| 授权与准备 | session/tunnel.rs → protocol::Request::Start → Worker::start / prepare | worker 必须独立校验与解析，前端不得提交可直接采用的系统路由或解析结果 |
| 配置校验的其他入口 | CoreService::config_for、core/adoption.rs、SessionService::check_owned → config::build | 核心安装、更新和普通检查也生成配置；不能让增加域名绕过导致这些操作开始联网解析或请求网络授权 |
| 正式配置 | profile/config.rs 的 compile、dns、policies | DNS、排除地址、IPv4 兼容和普通分流必须在同一次编译中组装，不能生成后追加几段 JSON |
| 启动就绪 | Worker::launch → platform/network.rs → network/routes.rs | 当前 covered 检查要求完整接管；有意排除会被误判为缺路由，简单跳过覆盖检查又会误报就绪 |
| 同一 worker 内的失败恢复 | Worker::actual、prepare(previous)、launch | 现在 actual 只有 ConnectionInput。新增域名解析后，重新 prepare(previous) 会得到新的 IP，无法恢复旧连接的实际排除范围 |
| 清理与崩溃恢复 | Worker::Resources / cleanup、RuntimeService、platform/network.rs 的进程记录 | 短期 DNS 核心也需要真实退出、残留身份校验和目录所有权，不能只依赖局部变量 Drop |
| 展示 | worker Snapshot → SessionService::snapshot_for → core.ts / activity.ts | 活动提示必须根据已确认运行结果，不能读取草稿或把临时 DNS 进程显示成代理已连接 |

重构范围限制在这些连接、进程和路由边界；节点导入、更新下载算法、托盘菜单和通用后台调度不重做。

## 12. 数据分层：一个意图，一份运行结果

### 持久化意图

- Policy 增加 bypass_tun: bool，对外名称 bypassTun，缺省 false。继续使用现有 proxy / direct 出口，不增加第三种出口或另一套规则类型。
- Routing::normalized 同时验证绕过选项的适用条件和地址保护边界；即使从 IPC 或磁盘读入，也拒绝代理、固定来源或子域名条件携带绕过。禁用规则保留合法偏好，但不参与本次目标收集。
- 沿用 schema 5 和 routingRevision，不新增独立的绕过修订或迁移框架。旧 profile 和 startup.lastConnection 中缺字段的 Policy 都按 false 读取。
- ConnectionInput 继续只表达冻结的节点、规则、来源版本、核心版本和连接选项；有效规则的 bypassTun 自然参与 fingerprint。解析 IP、查询时间、随机端口和密钥不进入此指纹，也不写进 lastConnection。

### worker 内部的运行结果

新增小型、用途明确的运行数据，建议放在 profile/bypass.rs 和现有连接准备模块：

| 数据 | 内容与所有权 |
| --- | --- |
| BypassTargets | 从已规范化且启用的规则提取精确域名、字面 IP / CIDR及错误归属；可由意图纯计算，无 I/O |
| ResolvedBypass | 精确域名到真实 IP 的固定映射，以及去重后的排除前缀。完整性与保护范围校验后才能构造 |
| RunningConnection | ConnectionInput + ResolvedBypass；仅 worker 保存，代表已确认实际连接，也用于同会话回退 |
| Prepared | 继续承载受信核心路径、私有配置、会话目录和活动端点，改为持有 RunningConnection，不再保留一份重复 input |

NetworkExpectation 从同一份 ResolvedBypass 派生；DNS 编译、TUN 排除、路由核验不各自再收集或解析一遍目标。

Worker::actual 和 Started::actual 改为 RunningConnection。控制端 SessionService::applied 和设置中的 lastConnection 仍保存 ConnectionInput。因此，恢复应用后的新连接重新解析；切换失败恢复当前旧连接则复用旧 ResolvedBypass。

## 13. 域名准备：复用官方核心，不实现 DNS 协议

### 选择短期、无 TUN 的核心实例

当前版本没有可直接采用的 resolve CLI 子命令。选择由授权 worker 启动一个短期 DNS 核心，使用相同的已验签受保护程序：

1. 配置只有本地 DNS transport、独立本机控制端点和必要的网络入口约束；没有 TUN、代理入口、节点凭据、外部面板或 Fake-IP 缓存。
2. 通过核心鉴权 GET /dns/query 查询 A / AAAA。DNS 查询、CNAME 跟随、上游协议和系统适配仍由 sing-box 处理；Rust 只校验 JSON 状态、问题与 IP 结果。
3. 一次连接准备最多一个短期实例，处理全部绕过域名。只有字面 IP 的规则不启动它。未启用绕过时完整跳过此路径。
4. 解析结束且临时实例真实退出后，才允许停止旧 TUN 并切换。它不注册为当前运行核心，不产生代理会话成功状态。

普通系统 getaddrinfo、tokio::lookup_host 或旧核心的默认 DNS 查询都不能作为替代：旧连接可能返回 Fake-IP 或上一会话固定结果。壳不在失败后自行换用公共 DNS / DoH 或用户配置的代理出口；上游选择沿用已验证的核心 local 语义。

### 独立上游是实施门槛

短期核心必须通过现有物理网络解析路径工作。平台层只负责确认独立于本应用 TUN 的默认接口；核心配置使用该入口和 local transport，不在 Rust 收集并实现一套 DNS 服务器调度。沿用既有多网卡与其他 VPN 的边界，不新增网卡选择界面。

Windows / macOS 的 local 上游与 Linux systemd-resolved、普通 resolv.conf 必须分别验证，尤其要覆盖“旧 TUN 正在运行”的情况。不能仅凭结果不是 Fake-IP 就宣称路径独立，也不能把旧会话的真实 hosts 回答当成新解析成功。若官方 local transport 在某条支持路径上不能满足这一点，应在第一阶段停止扩展实现并修订解析接入方案，不绕过保护或把问题推到用户手工停代理。

当前批准的 Windows 1.14.4 已确认带 with_clash_api。域名绕过需要该能力；缺少时在准备阶段明确报错，字面 IP 绕过与原有非绕过功能仍不依赖它，不把普通活动采集改成连接的强制条件。

### 复用两处现有基础能力

- 将 activity.rs 中端点创建和鉴权 HTTP 的公共部分提到 runtime/control.rs。只提供固定的连接读取、A / AAAA 查询方法；地址固定为本次 127.0.0.1 端点，禁止重定向、系统代理及前端指定 URL。活动采集和 DNS 准备共享这些边界，各自保留适用的响应上限与生命周期。
- 将 runtime.rs 私有 Process 的 Child、进程组 / Job、reader 和真实退出处理提到 runtime/process.rs，供原有校验 / 主核心和短期 DNS 核心共用。保留原有超时、错误、脱敏和退出语义，不做通用进程执行器。

控制端口被抢占、核心早退或绑定失败必须使准备失败。DNS 结果只有在同一个受保护核心启动确认、请求前后直接检查 Child 仍存活后才能采用；不能把“某个本机端口返回 200”当成可信核心。端点 secret 仅在私有配置和进程所有者内，加入现有日志脱敏，不传回 WebView。

建议首版内部预算：最多 32 个去重精确域名、最终最多 64 个去重排除前缀；DNS 查询最多 4 个并发，单请求 5 秒、整批 30 秒、单响应 64 KiB。正常无记录与超时 / SERVFAIL / 格式异常分别处理，不接受截断或部分成功集合。这些限制不做成设置项；边界数值要在原生验证后确定，不以提高上限掩盖失败。

## 14. 编译入口重整：检查与正式运行分开

profile/config.rs 保留普通策略的单一编译实现，对外区分两个明确入口：

| 入口 | 调用者与行为 |
| --- | --- |
| build_check | CoreService::config_for、core/adoption.rs 间接调用、SessionService::check_owned 和对应测试；只做意图 / 核心语法检查，不解析、不启动短期核心、不安装路由 |
| compile_runtime | 授权准备流程；必须接收完整 RunningConnection 和现有文件 / 缓存 / 活动绑定，缺解析结果即错误 |

两者共享正常 DNS、路由和规则集的生成代码。检查用途可以为绕过域名生成空 hosts 映射以核对配置形状，但这类配置仅供 check，不能作为 Prepared 的正式运行配置；正式入口强制要求每个目标域名有完整有效结果。不得通过默认空 map 或忽略开关，让遗漏参数的调用者悄悄启动无排除配置。

正式配置一次生成：

1. TUN inbound 的 route_exclude_address 使用 ResolvedBypass 中的前缀，其余 stack、strict_route、接口名和双栈地址沿用现状。
2. DNS 增加仅供本次绕过精确域名使用的 hosts transport，predefined 来自同一运行结果，不修改系统 hosts 文件。
3. 精确绕过域名的 A / AAAA 规则放在普通本地域名、IPv4 兼容空 AAAA 和用户 DNS 投影之前，确保得到已排除的真实地址；这个优先级与功能合同一致。
4. 绕过精确域名的 HTTPS / SVCB 查询由核心成功空答，避免额外地址提示跳出固定集合。其他查询类型沿用原有直连 DNS 处理，不在壳里解释其内容。
5. 普通分流、Fake-IP 持久化、规则集和活动绑定仍由原有编译流程产生，不做生成后的 JSON 补写，也不注入第二套流量匹配规则。

旧 Fake-IP、程序独立 DNS 和内部缓存继续遵循功能文档的边界；首版不通过清空系统缓存、重写缓存数据库或添加特殊流量嗅探来追补这些地址。

## 15. 路由核验与平台职责

### 从全覆盖改为按本次预期核验

现有 network::observe 无参数，并把“接口存在”“路由覆盖”和“停止清理”耦合到同一查询。调整为：

- 平台读取网络事实：接口地址、自动接管路由、相关策略表和必要的有效路由查询结果。
- 公共层按 NetworkExpectation 判断：应接管的范围仍完整覆盖，声明排除的范围没有被本应用 TUN 接管。
- 停止和 require_clear 只读取接口 / 资源释放事实，不要求传一个空排除集合来冒充启动核验。

排除不等于忽略检查。不能仅把排除段补回 covered 的并集：若核心根本没有执行排除，原来的全覆盖也会通过这种检查。必须同时验证接管补集和排除范围；接口连接路由与核心自动接管路由分开识别。

从现有 routing.rs 的 network / overlap 和 network/routes.rs 的数值范围计算中抽出小型 ip_network.rs，统一规范化、交集和有界区间运算。它只处理 IP / CIDR，不识别域名、规则集或业务流量，不成为新的路由引擎。地址族、/0 和 IPv6 最大边界必须正确处理；绕过目标首版拒绝 IPv4-mapped IPv6，避免跨地址族表达跳过保护校验。不能靠字符串前缀判断保护范围。

### 三个平台共享核验原则，保留原生读取

| 平台 | 调整范围 |
| --- | --- |
| Windows | 复用 IP Helper 读取，保留真实接口、双栈地址和路由信息；确认排除后核心自动路由已拆分，并以系统有效路由查询核验目标不会选中本应用 TUN |
| Linux | 保留 ip -j 的现有路径，核对本次核心的策略表与选择规则，再核验扣除排除后的覆盖及目标路径；不能把任意一个指向表的条件规则当成全局生效 |
| macOS | 保留 netstat / route 读取，支持官方自动路由原本排除保留段的拆分形式，再扣除本次排除；临时系统 DNS 的安装、检查与释放仍由 Dns 管理 |

可把现有按系统条件编译的读取代码移到 network/windows.rs、linux.rs、macos.rs，network.rs 保留统一入口，routes.rs 保留纯校验。只在这些职责上拆分，不更换平台适配方式。

声明排除后的有效路径可以是其他系统接口，也可能是该地址族没有可用上游。不能把“没有 IPv6 公网路由”冒充“仍走本应用 TUN”，也不能把排除安装成功冒充目标可达；不新增外网探测。核验有界，超限 / 输出截断视为失败，禁止只核验读取到的前一部分路由。

主核心仍是唯一系统路由写入者；Rust 只提供约束和读后核验，不额外执行 route add / delete、修改持久 DNS 或复制核心的防火墙规则。

## 16. 事务边界、失败恢复与临时进程清理

将 worker.rs 中已有 prepare 提取到 session/tunnel/preparation.rs；域名查询的短期进程封装可放在同目录 resolver.rs。worker 保留命令响应、一次替换和一次恢复的编排，不引入通用工作流或事务框架。

新连接顺序固定为：

> 校验意图和受信材料 → 确认独立解析入口 → 解析并冻结绕过结果 → 一次编译并由核心 check → 确认临时解析进程退出 → 停旧连接 → 启动候选 → 按同一运行结果核验路由 → 安装 / 核验临时 DNS → 提交运行事实。

| 结果 | 行为 |
| --- | --- |
| 解析、配置或候选 check 失败 | 清理候选准备资源，保持旧进程、DNS、固定解析结果和排除范围；返回操作错误，不提交新 applied |
| 候选启动或网络就绪失败 | 清理候选后，最多一次使用旧 RunningConnection 重新编译并启动；这条恢复路径不调用域名解析 |
| 用户停止、取消、退出 | 取消准备，不恢复旧连接；等待临时解析和正式核心真实退出，再释放资源 |
| 启动就绪后成功意图保存失败 | 沿用现有停止并清理行为，不把未持久确认的候选报告为连接成功 |
| 任意子进程 / reader / 目录收尾失败 | 保留原资源所有者和错误，进入现有 cleanupRequired，阻止下一次启动；重试清理同一对象，不吞错后新建所有者 |
| 应用重新打开后的恢复 | 使用 lastConnection 的业务意图，走全新解析；不读取旧会话 IP 结果作为新连接输入 |

必须区分当前会话资源与候选准备资源。候选创建后立即登记其私有目录和短期进程所有权，异常返回也携带待清理资源，不能在 prepare 的错误分支只 remove_dir_all 后丢失仍运行的进程。普通准备错误和清理失败使用不同结果，避免“有旧 PID 就一律当作准备失败已安全恢复”。

现有 platform/network.rs 混有 PID、启动身份、映像路径和进程组恢复。将这部分抽到 platform/process/record.rs，复用原有身份验证，只允许 Tunnel 与 Resolver 两个固定用途、固定记录文件：

- 主核心继续使用 network-process.json；短期核心使用单独的 preparation-process.json，不能覆盖当前核心记录。
- 当前目录仍使用 runtime/current.json；准备目录增加单个 runtime/preparing.json。均只记录已校验的随机会话 ID，不接受控制端传入路径。
- worker 在认证和取得机器级租约后，先处理上一 worker 留下的受保护准备资源，再接纳新准备，防止新记录覆盖旧残留。主 TUN 残留仍核对原记录处理。
- 正常流程在进程与 reader 全部退出后撤销对应记录、删除对应目录；崩溃恢复仍核对 PID 复用、启动身份、实际映像和受保护路径，不扫描 / 猜测进程，不删除其他应用接口或 DNS。

这些记录只服务本功能的两种受管核心用途，不建立进程注册中心、持久网络服务或新的恢复循环。原有核心版本回退规则保留；DNS 准备失败归为 Preparation，不误判为新核心损坏而触发版本回退。

## 17. 授权协议、前端与变更清单

授权请求仍只发送 ConnectionInput。worker 独立重验规则、字面地址和解析结果；不新增允许控制端提交系统路由、核心路径、解析服务器或最终 JSON 的命令。

握手协议从 5 升为 6，明确拒绝不认识绕过语义的旧 worker；这是授权协议版本调整，不是应用版本或设置 schema 升级。2 MiB 控制消息上限保留，运行 IP 映射不经 Poll 往返。

运行 Snapshot 只新增 running_bypass: bool，依据实际已确认的 RunningConnection 派生。SessionService 和前端类型透传这个事实；候选准备、保存或操作失败均不能提前改值。活动提示只读这个运行字段，不新增旁路活动采集。

| 文件 / 范围 | 拟修改内容 |
| --- | --- |
| profile/routing.rs、profile/connection.rs、settings.rs | 规则字段、纯校验、缺省兼容、运行意图指纹；保持保存无 DNS |
| profile/bypass.rs、ip_network.rs、lib.rs | 目标收集、已解析结果的完整性和保护校验，共享必要的 IP 运算 |
| profile/config.rs、core/mod.rs、session/mod.rs | 分离检查与正式编译入口，检查所有 config::build / compile 调用者；保持核心安装、更新和配置检查不联网解析 |
| session/tunnel/worker.rs、preparation.rs、resolver.rs | 当前 / 候选所有权、一次解析、正式启动、旧实际结果恢复、取消和资源回收 |
| runtime.rs、runtime/process.rs、runtime/control.rs、activity.rs | 复用子进程生命周期与固定鉴权接口，删除迁出的重复实现；保留活动独立可用性 |
| platform/network.rs、network/routes.rs、按系统的读取文件、platform/process/record.rs | 有意排除与应接管范围核验、必要的有效路由读取、两种固定用途的残留记录 |
| session/tunnel/protocol.rs、tunnel.rs、platform/authorization/handshake.rs | 运行旁路状态、准备进度、协议拒旧及消息边界；不放宽管理员命令能力 |

| scripts/ui-fixture.mjs、相关 Rust / 脚本夹具 | 补齐缺省字段、待应用 / 实际状态差异和失败结果，不让夹具伪装为真实网络验证 |
| 功能与开发文档 | 实现完成后更新 routing、core、activity、architecture、development、usage 中受影响的说明；导航只维护 docs/README.md，并删除本计划 |

以上是完整触达范围，不要求为列出的每个模块再造一层抽象。新增模块只在承接现有职责或被两个真实调用方共用时成立；不同时重构整个 SessionService、设置存储、更新系统或托盘。

## 18. 实施顺序、回归与本轮证据

### 第一阶段：先验证最容易推翻方案的核心 / 平台假设

在独立验证用例中确认：

1. 批准的 1.14.4 / 1.14.5 在五原生目标上，均能提供所需控制 API、hosts 固定回答和地址排除配置。
2. “无旧 TUN / 有旧 TUN / 旧核心持有旧域名结果”三种条件下，新准备使用独立物理解析路径；Windows 严格路由也不阻止同一受信核心的短期解析。
3. 核心实际拆分路由后，三个系统的读取结果可以按本次预期区分有效排除与接管缺失；停止、强杀和取消不会留下新增资源。

本阶段不先做 UI，也不通过降低 strict_route、停掉旧连接后才解析、退回系统默认解析或忽略失败，让能力验证看起来通过。核心能力 / 独立解析入口不成立时，先修订该接入点，不继续堆叠兼容分支。

### 第二阶段：一次贯通实现共享边界

按“IP 与意图校验 → 已解析运行数据及进程所有权 → 核心查询与双入口编译 → 就绪 / 释放核验 → 前端状态”实施。每一步补相应回归，最终交付仍是同时支持精确域名和 IP 的完整功能，不把只加 JSON 字段作为完成。

### 必要回归

| 层次 | 重点 |
| --- | --- |
| 纯模型 / 设置 | 默认兼容、非法组合、禁用规则、保留网段、IPv6 边界、重复目标、修改开关影响指纹、仅解析结果改变不影响待应用 |
| 编译 | 无绕过输出不变、正式输入缺映射拒绝、DNS 固定回答优先级、HTTPS / SVCB 空答、IPv4 兼容例外、普通策略顺序保真、check-only 配置不能用于正式准备 |
| 生命周期 | 准备失败旧连接不动；启动失败恢复同一旧 IP 集合；取消与迟到结果不提交；短期核心退出失败、清理重试和 PID 复用保护；最后成功意图保存不包含解析 IP |
| 路由纯校验 | 合法排除、核心忽略排除、额外缺一段接管、重叠 CIDR、缺策略选择、部分 / 截断输出均有明确结果，不能只测 happy path |
| 前端 | 弹窗与列表出口切换一致、修改保护、规则禁用、子域名限制、待应用与旧实际状态、最小窗口和键盘操作 |
| 真实官方核心 | 在隔离入口下验证 DNS JSON、固定多 A / AAAA、空回答及查询失败；端口占用、假 HTTP 响应和核心早退不能被接受；配置检查与实际 DNS 查询分开报告 |
