# Sing Shell 更新能力与应用生命周期整改方案

状态：设计待实施。此文是本主题唯一计划，不代表 v0.1.0 已具备所述能力。

## 1. 目标与调查基准

将 SoDeck 已有的更新行为落实到 Sing Shell：应用拥有更新任务，自动检查、明确下载、可靠缓存、显式应用、统一退出，客户端与发布产物使用同一契约。先整改现有应用状态和进程生命周期，再接入更新，避免在页面按钮中拼接一条旁路。

调查日期为 2026-11-26。Sing Shell 基准为 `32e05c047d369124fc582e8f166e65e4e95b87f4`，已发行 v0.1.0 的包来源为 `7bc1af7f728e6a658c6f6f3f538aacbdefcd2fe9`。SoDeck 参考基准为 `323d0bd5911bb281ebae8a17d519011734b7cc82`。本轮进行源码和发行资料调查，不将静态风险判断写成已经复现的运行故障。

## 2. 已确认现状与需要解决的问题

| 当前事实与位置 | 接入更新时的影响 | 整改方向 |
| --- | --- | --- |
| `main.rs` 的 `SharedCore = Arc<Mutex<Core>>` 包住所有业务操作 | 校验等待期间快照和退出也要争同一把锁；继续放入下载/安装会扩大阻塞 | 分离应用协调、进程、存储和更新，长操作持操作票据而非整应用状态锁 |
| `core.rs` 同时保存设置、管理子进程、收日志，并在 `snapshot → refresh` 中处理退出与销毁 | 读状态可能执行清理；页面停止刷新时，异常退出也不能及时独立投影 | 进程服务独立监督真实退出，快照只读 |
| `check_command` 等待最多 15 秒，`terminate` 同步等待进程和 reader；无统一取消入口 | 退出与校验/准备更新竞争，清理耗时不应卡住原生事件循环 | 统一接纳和取消；阻塞等待放 worker，收尾超时保留事实与重试能力 |
| `Settings` 只有 `corePath/configPath`；`save` 一律要求核心停止 | 不能直接将自动检查、下载网络等偏好塞进同一保存入口，否则运行中也无法改偏好 | 引入带修订的设置存储，区分偏好修改与运行选择修改 |
| 设置写入采用临时文件后 rename，但没有同步落盘；未知字段被拒绝 | 扩展配置要明确旧版迁移、未知版本和损坏文件处理 | 一次迁移到有 schema 的设置；同步写入、替换与失败保护 |
| 当前核心是用户选择的外部可执行文件，`version` 只检查退出码成功 | 缺少受管安装归属、准确版本和候选身份，不能安全覆盖用户文件 | 区分外部与受管来源；解析版本、检查原生架构、使用版本目录 |
| `main.ts` 全局 `busy` 时停止轮询；一次操作等待最终结果 | 下载时会冻结其他区域的事实和日志；刷新/关页容易影响交互投影 | 操作接纳回执、分区状态和独立刷新；前端不拥有任务 |
| `ExitRequested` 直接锁 Core、调用 stop；没有统一重启/安装交接 | 原生退出可能阻塞；Tauri 重启的新进程可能遇到旧实例锁尚未释放 | 所有退出与更新重启走同一后台收尾；提供有界实例锁交接 |
| `tauri.conf.json` 无 updater 公钥；发布包无 `.sig` 和更新清单 | Latest 不能代替客户端更新协议，现有包无法进入可信安装链路 | 独立 updater 密钥、签名产物、机器可读清单与真实升级验收 |
| `package.yml` 当前先上传草稿，再本机验收，报告靠后续人工汇总 | 签名、同源摘要、五平台完整性及重复上传需要集中核对；验收失败不应重建成功包 | 构建上传 Artifact、独立实际包验收、汇总后准备草稿 |
| v0.1.0 只有启动 smoke 和核心转发测试，没有壳自身升级测试 | 包能启动不等于原地替换、配置保留与重启成功 | 保留既有检查，另验真实旧版到新版安装链路 |
| GitHub 仓库目前为 private，现有 CLI 查询使用维护者登录 | 不能把维护者可下载误认为普通客户端可匿名更新 | 先确定公开发行入口，不向客户端内置仓库凭据 |

整改仅处理这些链路中与更新直接相关的职责和缺陷。已通过的核心启停、配置相对路径和五平台包验收继续保留。

## 3. 功能合同与边界

### 3.1 沿用 SoDeck 的行为

1. 默认开启每日检查。启动先恢复缓存，再延迟约 10 秒尝试；成功全量检查后约 24 小时再检查，失败或部分失败至少间隔 15 分钟再试。调度由 Rust 应用服务拥有，不依赖页面加载、前端 ready 或 sing-box 是否运行。
2. 自动检查不自动下载、不切换核心、不重启。关闭自动检查只停止接纳新的自动任务；手动检查、在途任务收尾和离线缓存恢复继续有效。
3. 展示当前/候选版本、说明、检查时间、进度、具体失败与重试。可选择应用和受管核心一起下载；最多两个具体下载任务，不建设无限队列。
4. 下载完成只进入“待应用”，由用户明确选择“重启并应用”。下载不结束正在运行的 sing-box，准备完成不热替换它。
5. 全量检查、逐项重试、自动检查共用一套发现及任务入口。失败保留上一次有效候选，不能用“已是最新”掩盖网络错误；已准备包不被定时检查降级或清空。
6. 同一组件按正式 SemVer 升序比较，只接受更高正式版本。跳过草稿/预发行；首个正式候选损坏或缺平台就报错，不静默退到另一个历史包。
7. 应用更新使用 Tauri 官方 updater 签名和安装。Windows、macOS、Linux AppImage 支持应用内安装；DEB 显示“使用系统安装方式更新”，提供官方发行入口，不自行调用 sudo 或修改系统包库。
8. 下载网络提供原始地址优先、内置备用与自定义 HTTPS 地址、逐地址诊断。网络设置用于后续任务；在途任务保持自己的配置快照。

### 3.2 本方案包含的两个更新对象

| 对象 | 归属与来源 | 更新行为 |
| --- | --- | --- |
| `sing-shell.app` | Sing Shell 自身的正式 Release | 下载已签名应用包，应用内安装并重启 |
| `sing-shell.engine` | 用户明确选择由应用管理的官方 sing-box | 从 `SagerNet/sing-box` 获取对应原生程序，校验并放入应用数据目录，重启时切换 |
| 外部 sing-box | 用户选择的绝对文件路径，包括已有 v0.1.0 选择 | 显示“外部核心，手动管理”；不覆盖、不删除、不后台升级该文件 |

“安装官方核心”是明确动作，不把现有外部文件静默收归应用管理。不安装通用插件系统，不把 sing-box 当作 SoDeck 插件套用 API 主版本；它只需要具体命令行能力和配置兼容检查。

普通启动仍不自动运行 sing-box，更新重启后同样由用户点击启动；应用更新前明确提示会中断当前代理。这保留现有启动约定，不引入一次性自动启动票据或隐含的后台运行。本次不包含开机启动、托盘、系统代理、TUN 提权、订阅和节点管理。

### 3.3 已确认的发行方式

用户已确认公开 `BgaSol/sing-shell`，源码与正式 Release 使用同一仓库，沿用 SoDeck 的发行方式。不新增独立发行仓库或跨仓库发布凭据。

本轮仅记录方案，尚未更改实际可见性。实施时在发布准备阶段公开该仓库，并以无登录客户端验证标签、正式 Release、清单和包均可匿名读取；生产源固定为该仓库。

禁止将维护者 PAT、Actions token、私有 updater 密钥或代理鉴权秘密编进前端、可执行文件或公开配置。正式验收包含无维护者凭据的匿名发现和下载。

## 4. 目标代码组织

保持单个 Tauri 应用和现有 TypeScript/Vite 工程。建议边界如下，文件只在对应步骤真实实现时创建：

```text
src-tauri/src/
  main.rs                 Tauri 装配、命令、系统事件转接
  app.rs                  Application 组合、短操作接纳与关闭边界
  settings.rs             设置 schema、迁移、修订、落盘和实例锁
  runtime.rs              原 Core 中的 sing-box 校验、启动、监督和停止
  logs.rs                 有界记录和输出采集（运行时、更新均实际使用）
  platform.rs             现有进程组及必要安装环境识别
  lifecycle.rs            exit / restart / install-and-restart 的唯一入口
  updates/
    mod.rs                两个固定组件的类型、快照与操作合同
    service.rs            初始化、调度、接纳与收尾
    release.rs            GitHub 发行发现和不可变候选
    network.rs            实际 HTTP、线路、限额和诊断
    application.rs        Tauri updater 适配及应用缓存
    engine.rs             受管 sing-box 下载、解包、验证与激活
src/
  main.ts                 页面组合与订阅
  core.ts                 类型化 Tauri IPC 入口
  runtime.ts              当前运行配置、状态、日志控制器
  updates.ts              更新页和下载网络设置控制器
  update-model.ts         组件状态到文案/可操作项的纯投影
```

`Application` 组合 `SettingsStore`、`RuntimeService`、`UpdateService` 与退出协调。原 `Core` 拆解后删除或仅在一次迁移提交中保留短暂调用适配，不长期保留旧 Core 和新服务两套状态。

只保留两个具体更新实现，以 `match ComponentId` 分派。不建立插件注册表、通用安装器 trait 层、工作流引擎、消息总线、跨仓库公共 crate 或动态组件扩展点。共享的是实际出现两次的发现、传输和错误类型，不是把应用安装与引擎切换混成同一动作。

需要一起追踪的现有调用面：

| 文件/入口 | 随整改必须同步的内容 |
| --- | --- |
| `src-tauri/src/lib.rs`、`main.rs`、`core.rs` | 公共模块导出、Tauri managed state、命令注册、startup/setup、退出回调与旧 Core 清理 |
| `src-tauri/tests/lifecycle.rs`、`real_core.rs`、`tests/fixtures/core.rs` | Core 调用迁入真实服务；保留原本的坏配置、锁、相对路径、长日志及端口回收断言，增加取消/迟到结果场景 |
| `src/core.ts`、`main.ts`、`index.html`、`style.css` | IPC DTO、页面挂载、ready/smoke 时机、分区刷新、原有按钮和新更新入口；不留下旧全局 busy 旁路 |
| `src-tauri/Cargo.toml`、Cargo/npm 锁文件、`build.rs` | 必要生产依赖及测试 feature；保留 Windows 原生测试 manifest 处理，测试夹具不发行 |
| `tauri.conf.json`、独立发行配置、capabilities | 本项目公钥、生产签名产物、精确所需 capability；前端继续走自有 IPC，不增加任意文件或命令执行权限 |
| `package.json`、两个现有工作流、`verify-package.mjs`、`verify-binary.mjs`、`smoke.mjs` | 工程命令与 CI 同步，复用原生目标规则，实际包版本/签名检查，新升级夹具隔离生产数据 |

迁移时用调用搜索核对这些入口，并删除被替代的旧状态与事件；不能只让新更新页调用新服务，而运行页/退出路径仍操作旧 Core。

## 5. 状态、并发与命令合同

### 5.1 唯一事实来源

- SettingsStore 拥有已提交设置与修订；RuntimeService 拥有进程身份、真实退出与输出 reader；UpdateService 拥有检查时间、两个组件候选、进度及准备结果。
- 应用接纳只维护 `open / closing / handing-off` 与在途操作归属。更新子模块不再各自维护第二个全局 closing/busy。
- 操作票据固定组件、操作 ID、候选版本/目标/摘要及相关配置身份。旧任务只允许提交给自己的 ID；切换外部核心、关闭或新任务接纳后，迟到结果不覆盖新事实。
- 网络、配置校验进程、解压、签名校验、等待进程退出和安装都不能持应用状态锁。使用现有 Tauri runtime 与有限 worker；进程 supervisor 独占 Child，短锁只维护可读投影。
- 快照读取不清理子进程、不检查网络、不写缓存。异步事件仅通知重新读快照；漏事件、页面重开与重载均能恢复当前事实。

### 5.2 固定的操作接纳规则

| 操作 | 可并行范围 | 必须拒绝或协调的情况 |
| --- | --- | --- |
| 读取运行/日志/更新快照 | 始终可读，保留上次有效状态 | 读失败单独展示，不清空其他分区 |
| 启动/停止/配置校验 | 与更新检查和包下载可并行 | 同一个进程变更只接纳一项；关闭后拒绝启动与新校验 |
| 修改自动检查/网络偏好 | 核心运行时允许 | 按 expectedRevision 保存；不改变在途网络配置 |
| 更换核心、导入配置 | 核心停止时允许 | 与配置提交、最终更新应用互斥；原生文件框返回后重新核对接纳和配置身份 |
| 全量/单项更新检查 | 一轮更新检查；普通运行不受影响 | 下载或最终应用期间不新接纳检查，自动轮次稍后判断 |
| 下载所选更新 | 最多两个组件，各一项 | 重复点击不重复入队；应用/关闭期间不接纳；失败释放对应票据 |
| 重启并应用 | 先固定本次选择和 prepared 身份 | 检查/下载/校验未收尾时明确等待或拒绝，不忽略在途任务 |
| 普通关闭 | 可请求取消检查、下载及短校验 | 等实际取消和进程收尾；不能把发出取消信号当成清理完成 |

Runtime 状态至少区分 stopped、checking、starting、running、stopping、failed；`running` 仍只表示子进程存活，不承诺网络通畅。子进程结束和错误的输出采集由 supervisor 独立完成。停止/reader 收尾有期限，超期保持 stopping/failed 并可重试，不能释放未知仍占用的进程资源后宣布成功。

UpdateItem 使用小型状态集合 `idle / checking / current / available / downloading / preparing / ready / applying / error / unsupported / external`。错误携带 `stage`，已有候选和准备记录独立保存；总览 busy/待应用数量由实际项派生，不再添加彼此不一致的布尔标志。

### 5.3 IPC

运行命令沿用明确的启动/停止/校验语义。新增 `update_snapshot`、`check_updates(component?)`、`download_updates(components)`、`cancel_update(component)`、`set_update_preferences(expectedRevision, draft)`、`test_update_mirror(prefix)`、`open_update_release(component)`、`request_restart(applyComponents)`。

修改命令接纳后返回 `{ operationId }`，拒绝时立即返回明确原因。状态由快照和通知读取，任务属于应用、不随页面卸载终止。禁止前端传安装路径、任意下载 URL、签名、公钥或“已验证”标志；后端从固定候选解析。操作 ID、修订和取消只服务本次具体操作，不扩展为通用任务 API。

## 6. 设置迁移与存储

将旧的无 schema `{corePath, configPath}` 一次迁移为 schema 1：`schemaVersion`、`revision`、`engine`、`configPath`、`updatePreferences`。`engine` 为未配置、`external {path}` 或 `managed {version, target}`；受管程序路径只能由应用数据目录、版本和目标推导。

- 旧的 corePath 一律成为 external，配置仍引用原文件及其父目录。迁移不复制、上传、编辑或删除用户配置。
- 迁移前保留原设置备份；解析成功、目标记录写入并同步成功后才提交。新安装默认开启每日检查，旧选择完整保留。
- 未知 schema、损坏或读写失败保留原文件及错误，不按默认值覆盖。存储错误独立于核心运行错误，不靠错误文案前缀决定是否允许写入。
- 写设置使用临时文件、`sync_all` 与目标系统可验证的替换；写入序列单独串行，不占应用全局锁。提交用 expectedRevision，冲突保留界面输入。
- 更新缓存单独使用版本化记录，只保存稳定候选、已验证 prepared 信息、检查时间。checking/downloading 等运行中状态不持久伪装恢复；启动时重新核对包和版本。
- 实例锁由应用整体拥有，释放在服务和子进程结束之后。参考 SoDeck 为旧实例退出与新实例启动的短暂重叠做约 2 秒有界重试；超时仍拒绝第二实例，不无限等待、不另建第二套选主协议。

旧版 v0.1.0 不能读取新 schema 时，保留备份供人工恢复；不提供应用内任意降级功能，也不宣称向下兼容。

## 7. 更新发现、候选和网络

### 7.1 应用发行

沿用 SoDeck 的 `core-update.json` 形式，但组件 ID 为 `sing-shell.app`，仓库固定为 `BgaSol/sing-shell`，标签为 `v<major.minor.patch>`。以标签引用按版本降序查对应正式 Release，不依赖仓库 Latest 返回值做版本选择。

清单包含 `id/version/notes/platforms`；每个平台至少有已固定的原始下载 `url` 与 Tauri `signature`，可补 `size/sha256` 用于产物核对，但不能替代官方验签。五个 Rust target 统一使用当前原生目标名；Linux 清单的在线应用包为 AppImage，不将 DEB 喂给 updater。

候选绑定 repository、tag、release/asset 身份、version、target、原始 URL 和签名/摘要。下载前再次核对候选身份；同版本附件或清单改变就要求重新检查，不悄悄替换本次目标。原站真实 404 才能证明标签没有正式发行而顺延；镜像 404、限流、私有源或损坏清单不能显示“已是最新”。

### 7.2 官方 sing-box 发行

直接适配 `SagerNet/sing-box` 的稳定 Release，不要求上游增加本项目清单。只选命令行核心包：Windows amd64/arm64 ZIP、Linux amd64/arm64 tar.gz、macOS darwin-arm64 tar.gz，不选择 SFW/SFM 图形客户端、legacy 包或 nightly。

保持两个明确的源适配：应用源读取自有清单；引擎源读取上游资产元数据。引擎使用原站 HTTPS GitHub API 返回的资产 SHA-256、资产 ID、大小与文件名固定候选，随后可通过备用线路下载字节。未签名的摘要元数据不接受仅由第三方镜像提供的值，避免镜像同时替换包与校验值；原站元数据不可获得时明确失败，已有准备包仍可离线使用。

若上游缺有效摘要、预期架构包或版本输出不符，停止自动准备，不退化成只看文件名或 `version` 退出码。摘要验证用于完整性及固定来源，不宣称具有 Tauri 应用签名相同的信任保证；不自建上游签名链或替上游发行未经验证的新标签。

### 7.3 共享传输

复用 SoDeck 已验证的传输逻辑与回归用例，删去 AppCore/插件日志等耦合后放在本仓库内部模块；不实时导入另一仓库源码。保持 API 与文件线路分别记健康状况、失败冷却、原站优先及有限回退，内置地址取移植时的已验证列表，支持最多 10 个自定义 HTTPS 前缀和逐地址诊断。

生产地址不得携带用户名密码；重定向限定跳数、scheme 和凭据传播。正常生产无需 GitHub token，测试 token 只能用于原始 API，不能发往镜像或跨主机跳转。

继承可验收限额：元数据单响应 2 MiB、包 512 MiB、元数据请求总预算 45 秒、包下载总预算 10 分钟，连接/读/取消均有超时。断流或验签失败清除本次 `.part`，换线路从头获取，不跨线路拼包，不做断点续传框架。未知大小展示真实已下载字节。

下载网络服从操作系统代理，但不需要 sing-box 已启动才能初始化。核心可能恰好承载系统代理，因此全部联网和包准备必须在停止核心之前完成；关闭后的安装及激活只能使用本地已验证材料，不能再请求清单。

## 8. 应用更新链路

```text
启动应用 → 读有效设置 → 恢复并重验缓存 → 初始化一次调度
  → 自动/手动检查 → 固定候选 → 显式下载
  → 临时文件 → Tauri 官方验签 → 同步写入准备缓存
  → ready → 用户选择应用 → 统一关闭准备 → 再次离线验签
  → 停止 sing-box/收尾任务 → 官方安装器 → 原生重启
  → 新进程确认实际应用版本 → 清理已消费缓存
```

准备缓存保存目标、准备时当前版本、候选原始清单和包摘要。断电只留下包或只留下元数据不能成为 ready；同目标稳定记录最后提交。恢复时重新验签，安装时再次读取并验签实际将安装的字节，防止 ready 后被修改。丢失、篡改、跨目标和过期记录显示可重试错误，不从阶段名称推断验证成功。

安装失败保留可验证材料并返回仍可操作的窗口；不能先退出应用再去猜安装结果。Windows 安装器进程交接按 Tauri 官方实现验收，不把启动安装器等同新版本已运行。只有下次实际进程版本变化才确认应用升级成功。

只读 macOS DMG、无替换权限的安装位置、只读 AppImage 路径给出明确不支持原因及正常安装入口。开发模式不调用生产安装器，也不触发正式自动检查。`--smoke-test` 和默认测试实例同样禁用生产调度与安装，避免包验收时真的下载或升级自己；升级专项通过 test-fixtures 和显式隔离数据目录接入固定测试源，生产构建不提供该入口。

## 9. 受管 sing-box 安装、准备与切换

目录按 `engines/sing-box/<version>/<target>/` 保存，缓存与当前激活选择分开；最多保留当前、待应用和一个上一版本用于失败恢复，不建设历史版本市场。

```text
明确安装官方核心/检查已管理核心 → 固定官方候选
  → 下载并核对 SHA-256/大小 → 在独立临时目录解包
  → 校验原生架构和实际版本 → 用候选检查当前配置
  → 提交版本目录和 prepared 记录 → 当前旧核心继续运行
  → 显式重启应用 → 停止旧进程并等待退出
  → 重查本次配置与选择身份 → 原子提交受管核心版本
  → 重启后仍由用户明确启动
```

解包只接纳已固定上游布局中的目标可执行文件及必要许可证，不遍历执行压缩包脚本；拒绝绝对路径、`..`、盘符/UNC、符号/硬链接、设备、重复入口、错误平台、过量条目及超限展开内容。设置解包总量和文件数上限，并用恶意归档夹具验证，不能依赖扩展名安全。

执行 `version` 前检查 PE/ELF/Mach-O 原生架构；从输出解析并比对固定候选版本。Unix 执行位由明确文件设置，不用 shell chmod 命令。只运行上游固定候选，不接受 UI 传来的任意程序安装任务。

存在配置时必须用新核心执行 `check -c`，工作目录保持配置父目录。准备后配置选择或主文件变化要重新校验；外部规则资源不归应用所有，实际启动继续重新校验，不承诺与外部编辑器共享全文件树事务。无配置时允许先安装受管程序，启动仍要求有效配置。

新配置不兼容、解包/版本检查/落盘失败时保留原受管版本和外部选择；不停止旧核心、不修改用户配置。应用受管版本前旧进程必须真实结束，特别是 Windows 不能覆盖运行中 exe。

两个组件同批准备、同一次明确重启依次应用，但只承诺每个组件自己的提交结果，不构造跨组件原子升级。受管选择提交后若应用安装失败，如实展示已生效的核心选择与失败的应用项，不假装全回退或全完成；应用尚未重新启动时不会自动运行新核心。崩溃恢复以实际应用版本和已提交核心选择为准，剩余 ready 项仍需明确应用。

## 10. 退出、取消与重启的唯一链路

窗口关闭、正常退出、普通重启、更新重启全部请求 Lifecycle；原生 `ExitRequested` 回调只接纳/转接，不同步等待 Core 锁。只有 Lifecycle 完成必要收尾后设置 handing-off 并交给 Tauri 退出或重启，避免安装重启再被普通关闭逻辑拦截。

1. 短锁内封闭新修改、固定所选 prepared 及运行事实；检查文件框/设置保存是否仍在途。
2. 若用户取消则恢复接纳，保持当前运行；未进入最终退出前不能永久取消更新调度器。
3. 更新重启先离线重验应用包、受管核心、配置兼容性及候选身份。校验不通过仍保留当前运行，不提前停止代理。
4. 普通退出请求取消在途网络与短校验，等待 worker 的真实结束；不能一边写缓存一边释放实例锁。
5. 停止实际 sing-box 进程组、确认 reader 与进程收尾。失败显示实际状态，可重试；不调用安装器、不谎报已停止。
6. 应用受管选择、安装应用包，分别保存明确结果；安装失败回到可读可重试状态。此时代理已停止，需要界面准确提示。
7. 停止调度并释放其他资源，执行一次原生 exit/restart；新进程取得同一数据目录锁，重新验证持久状态。

不引入多窗口关闭投票、插件任务 DAG 或 SoDeck 工作台生命周期系统。这里只管理一个窗口、一个核心进程和有限更新任务。若沿用现有强制终止策略，必须继续文档化缓存落盘与 Unix 强制杀宿主的限制；不借更新需求顺带开发通用守护服务。

## 11. 前端行为

保留现有运行页，增加单一“软件更新”入口，显示“Sing Shell 应用”和“sing-box 核心”两项。外部核心显示手动管理及“改用应用管理的官方核心”，不出现可误点的覆盖操作。

更新页提供检查、下载所选、逐项重试/取消、每天检查开关、下载网络和待应用列表。全局只显示未处理更新数/待重启入口，具体进度和错误归所属项，不为每个后台错误弹系统通知。

移除跨全部页面的单一 busy。运行、日志、更新分别保留读失败和上次有效快照；下载期间日志继续更新，配置偏好仍可编辑。前端挂载只订阅/读取，不另开检查任务。刷新及页面重载不取消后台下载；明确取消才影响任务。

固定区域局部更新 DOM，不在进度刷新时重建网络表单、详情展开和日志滚动容器。网络草稿按实际值比较 dirty，冲突保留输入；关页可以保留草稿，退出时提供保存/放弃/取消，只有存在草稿时才询问。按钮是否可用从后端操作事实派生，后端仍做最终接纳检查。

## 12. 依赖与复用策略

保留 Tauri 2 / Rust、TypeScript 原生 DOM / Vite，不加 React、状态管理框架、数据库、Go FFI、运行期安装脚本或升级守护进程。

实施时需要的依赖均优先沿用 SoDeck 已选版本，新增生产依赖在对应实施提交列出用途并提交锁文件：

| 依赖类别 | 用途及选择 | 替代方案与边界 |
| --- | --- | --- |
| `tauri-plugin-updater` | Tauri 官方签名验证和平台安装，沿用 SoDeck | 自写安装器/验签不采用 |
| `reqwest`、按选定 features 所需的 `rustls` | HTTPS、系统代理、流式下载及受控重定向 | 不调用 curl/PowerShell；TLS provider 在进程入口按官方要求一次初始化 |
| `tokio` 的 time/sync 等必要 features | 调度、有限并发与取消/等待；使用 Tauri 现有 runtime | 不另建一套 async runtime，简单取消可用已有 watch，先不加独立取消框架 |
| `semver`、`sha2` | 版本排序、上游摘要和缓存核对 | 不手写版本字符串排序和散列算法 |
| `zip`、`tar`、`flate2` | 受管引擎的 Windows / Unix 两种真实包格式 | 不要求用户机器预装解包 CLI，不做插件包框架 |
| `tauri-plugin-opener` | 打开发行页或系统安装入口，复用 Tauri 标准适配 | 不拼 shell 打开命令 |

上述项目分别由 Tauri、Rust HTTP/TLS 与对应 Rust 上游维护，SoDeck 已固定使用；实施前复核固定版本的维护状态、许可证、漏洞与平台兼容，发现问题时先说明升级或替代原因，不把“当前在 SoDeck 使用”当作永久维护保证。未使用的 feature/依赖不先加入清单。

## 13. 签名、产物和发布整改

### 13.1 签名与首次交付

为 Sing Shell 单独建立 Tauri updater 密钥，公钥入配置，私钥只入维护者备份和 Actions Secret，不复用 SoDeck 身份。发行配置启用 `createUpdaterArtifacts`；正式打包缺密钥/签名就明确失败，普通开发构建不要求生产私钥。updater 签名不能冒充 Windows 发行商证书或 macOS 公证，这两项仍独立记录。

v0.1.0 没有 updater，不能通过追加一个清单使已安装客户端凭空具备该功能，也不覆盖它已发行的 8 个附件。首个含更新能力的版本建议为 v0.2.0，必须手动下载安装；从这个签名基线开始才能对后续版本做在线更新验收。版本号在实施交付时才修改，不在本方案中提前变更。

### 13.2 保持普通 GitHub Actions / Releases

在现有 `Package Sing Shell` 内调整阶段，不复制 SoDeck 的业务插件发布系统：

1. preflight 固定版本、源码、发行仓库和标签，确认已有正式版本不可覆盖。
2. 五平台原生 package 使用官方 Tauri 打包与签名，上传该平台 Artifact，包含包来源、目标、文件名、大小、摘要和必要 `.sig`。
3. 独立 native verify 下载原 Artifact，核对原生架构与签名，验收实际包及核心转发；失败只重跑对应 verify，不重新生成成功包。
4. 单个汇总步骤核对五份成功报告及同源摘要，生成 `core-update.json`，创建固定标签和同一份 Release 草稿并上传已验证字节。附件用实际输出名称，处理 GitHub 文件名规范化，不猜包名。
5. 明确发布同一草稿并设 Latest，不再推标签触发相同版本第二次打包。已正式发布附件不可覆盖。

已有有效 Artifact 时复用明确原始 run，不能选“最近一次运行”猜来源。缓存保持稳定，失败按实际失败的平台/验收/汇总重跑；不建设内部发行批次、证书审批链或全平台联动插件门禁。

`Check` 保留常规类型、格式、脚本和核心测试。`verify-package.mjs` 保留当前实际安装包和上游核心测试，更新后同时核对签名及包内应用版本；`smoke.mjs` 增加 expectedVersion/expectedTarget，不能只认 completed/ready。新增隔离升级验收入口，不让测试夹具进入发行包。

## 14. 实施顺序与每步完成条件

每一步形成一个可独立 review 的完整主题，代码、调用者、测试和正式文档在该步同步；不以创建空模块当作完成。

| 步骤 | 范围 | 必须达到的验收 |
| --- | --- | --- |
| A：职责和生命周期 | 拆 Core、只读快照、进程监督、短接纳锁、统一退出、设置迁移及实例锁交接 | 原有流程回归通过；校验中能读状态/日志和发起退出；旧设置无损迁移；停止失败事实保留 |
| B：应用更新纵向闭环 | 固定公开源、候选发现、官方 updater、缓存恢复、离线重验及重启安装 | 本地固定发行源中完成“发现→下载→验签→关闭→安装→新版本确认”；假签名、坏包、网络失败不破坏当前应用 |
| C：受管核心 | 官方程序安装、来源归属、平台适配、配置兼容、版本目录及切换 | 外部文件始终不变；候选失败旧核心继续运行；重启后选择正确；真实 SOCKS5 转发与端口释放通过 |
| D：完整 SoDeck 交互 | 调度、双项下载、网络回退/诊断、统一更新页及前端分区 | 无前端也能按约调度；进度不冻结日志/草稿；取消和旧结果隔离正确；下载期间不接纳应用 |
| E：发行和原生升级 | 独立签名、五平台 package/verify/汇总、清单及真实升级验收 | 五平台包与签名同源、匿名获取可用；安装位置及配置保留；不得只测新包启动就声称自动更新完成 |

B 使用明确本地测试源形成完整纵向链路；生产网络功能在 D 补齐，E 才承诺可发行。可以依步骤提交，但 A–E 未全部验收前不宣布整个自动更新整改完成。

## 15. 回归与验收矩阵

| 链路 | 必须覆盖的场景 |
| --- | --- |
| 设置/迁移 | 旧外部核心与非 ASCII 配置路径；损坏/未知 schema；写失败、磁盘满、修订冲突；网络偏好运行中保存；失败不覆盖原文件 |
| 核心生命周期 | 校验和启动取消；异常退出不依赖轮询；关闭与启动竞争；reader 收尾失败；重复停止/退出；新旧实例锁短暂重叠与真正第二实例 |
| 更新发现 | 标签 SemVer 排序；草稿/预发行跳过；首个正式坏清单/缺目标立即失败；原站 404 与镜像 404 区别；限流、无凭据私有源及候选在下载前变化 |
| 调度 | 无页面服务启动一次；10 秒/24 小时/15 分钟用可控时钟验证；开关、部分失败、休眠后恢复与取消关闭；单项重试不推迟全量周期 |
| 传输 | 流式大小限制、慢响应/断流、取消、有限重定向、错误签名后的换线、旧网络配置结果隔离；不能向镜像转发 token |
| 应用缓存 | 仅 part、仅元数据、坏字节、跨平台、同版本不同来源、ready 后篡改、离线重启恢复、安装前再验；失败保留可重试状态 |
| 受管核心 | 五个平台资产名；原生架构与版本不符；摘要缺席/不符；路径穿越与链接归档、解包限额；配置/规则不兼容；外部文件零覆盖；切换提交前后异常恢复 |
| 组合应用 | 两项同时 ready；先关闭后下载提交的竞态；停止失败不安装；受管切换成功后应用安装失败的真实分项结果；最终安装不联网；重复重启只交接一次 |
| 前端 | 操作接纳后重载；读取失败保留旧快照；下载期间日志继续；网络表单输入/选区/展开/滚动稳定；后端拒绝忙碌时真实反馈 |
| 发行 | 五原生目标 package + verify；签名、公钥、目标、版本、清单 URL/附件摘要一致；匿名新机器发现并下载；失败只复验原包；正式附件拒绝覆盖 |

原生平台专项：Windows 安装后的实际程序经 updater 更替并重新获取数据锁；macOS 从安装到可写位置的真实 app 更新，DMG 只读运行明确拒绝；Linux AppImage 原地更新且路径/权限正确，DEB 使用系统包管理升级并保留数据。全部验证旧/新实际版本、核心选择与配置路径保留、进程和端口收尾。

首个 updater 版本的升级测试使用本次签名基线和更高的隔离签名候选，执行生产安装逻辑；生产端不接受测试公钥/HTTP endpoint。之后补真实正式旧版到新版样本。不能把 v0.1.0 手工覆盖安装称为 updater 验收，不向 Latest 发布无意义的测试版本。

每步运行相关 `npm run check`、`npm run scripts:test`、`npm run test`、`npm run build`，新增入口与工作流同步。普通成功结果放提交/PR，长期缺陷转成测试；发行报告保留版本、原包源码、原始 run、Release、实际验证及跳过范围到 `docs/releases/`。
