# 托盘、登录自启与核心运行恢复整改方案

状态：实现已落地，等待五平台原生与实际包验收。原始设计：2026-11-26 基于 sing-shell `26c17085e6b8f51c91abc7641a01eee5f2e11209` 核对；对照 SoDeck `d5e44012e5a08008d3db9acbfb6bcd244d28e69c` 的桌面壳、登录项、实例激活和更新收尾。本文是后续整改依据，不代表当前 v0.3.0 已具备这些功能。本轮只新增方案和导航，不修改应用行为、版本、系统登录项或 Release。

## 1. 产品合同与范围

目标是登录后能够恢复工作、平时驻留托盘、用户主动停止后保持停止。应用仍是当前用户桌面会话中的普通进程，核心仍是受应用管理的子进程。

| 场景 | 验收行为 |
| --- | --- |
| 点击主窗口关闭 | 收起窗口，核心、下载及设置草稿继续保留；不触发退出或保存/放弃提示 |
| 首次收起 | 收起前说明一次返回和退出入口，确认且实际收起成功后记录；不增加每次关闭询问或新的关闭方式设置 |
| Windows / macOS / Linux | Windows 隐藏到托盘；macOS 使用菜单栏和 Dock 身份切换；Linux 最小化并保留系统窗口入口 |
| 后台入口不可用 | 保留或恢复可见窗口，显示原因，不能产生找不到入口的后台实例 |
| 登录后自动启动应用 | 默认关闭；开启后在当前用户下一次登录图形桌面时后台启动；手动打开仍显示窗口 |
| 应用启动时恢复核心运行状态 | 独立开关，默认关闭；上次成功运行且未主动停止才恢复；上次主动停止则保持停止 |
| 修改两个开关 | 立即生效，反馈实际结果；不立即启动/停止核心，也不改变当前窗口显示 |
| 再次打开应用 | 唤回同用户、同数据目录的现有窗口，不重复初始化、迁移设置或运行核心 |
| 托盘退出 / Cmd+Q / 真正退出 | 处理草稿，取消维护并等待收尾，停止核心后结束；本次会话不自动拉起 |
| 应用更新 | 使用同一退出链路；清理不抹掉恢复意图，新进程按开关决定是否恢复核心 |
| 自动恢复失败 | 明确展示原因，保留用户文件；一轮启动至多一次恢复用例，沿用已有一次版本回退，不循环启动 |

只保留“运行＋设置”两页；现有软件更新页扩展为设置页，增加置顶的“启动与窗口”分组。托盘固定提供状态、显示主窗口、启动/停止核心、设置、退出。异常状态可点击查看原因；普通更新和启动成功不抢焦点。此前功能方案中的后台可点击提示以托盘状态及问题入口实现，首版不引入独立通知中心或系统通知插件。

不增加系统代理、TUN 提权、登录前运行、系统服务、崩溃守护、定时重启、全局快捷键、多窗口或多配置运行。保留现有五个原生目标、独立应用更新身份和外部核心不被接管的边界。

## 3. 拆清四种状态，控制新增职责

| 状态 | 唯一事实来源 | 不应混用 |
| --- | --- | --- |
| 核心真实状态 | RuntimeService 的真实进程、观察结果和资源收尾 | 不用“下次想运行”伪造当前 running |
| 下次恢复意图 | CoreService 在成功启动、主动停止时持久化 | 内部清理、更新采用、崩溃、隐藏窗口不能改成停止 |
| 登录启动是否启用 | 操作系统当前登记和限制 | 不在 settings.json 保存第二个 enabled 并启动时重新登记 |
| 窗口是否收起 | 原生窗口和桌面壳 | 不决定核心生命周期，不作为登录来源的持久偏好 |

职责调整限于以下具体模块，不建立通用桌面框架：

| 模块 | 职责 |
| --- | --- |
| 新 `desktop.rs` | 单主窗口显示/收起、托盘菜单与投影、macOS 身份、模态保护、待导航、桌面问题反馈 |
| 新 `startup.rs` | 一次性 LaunchContext、重启参数归一化、一次核心恢复请求；不直接 spawn/stop 核心 |
| 新 `instance.rs` | 数据目录 Lease、仅“显示已有窗口”的本地激活通道、重启等待；不传配置或任意命令 |
| 新 `login_startup.rs` 及必要平台文件 | 当前用户登录项读取、修改、安装位置和归属检查；系统适配集中，不扩展成任务调度器 |
| 原 `lifecycle.rs` | 明确退出目标、单个草稿决策请求、封闭接纳、等待任务、停止资源、安装器交接 |
| 原 Application / CoreService / SettingsStore / RuntimeService | 分别组合与唤醒、核心用例、串行持久化、真实进程资源；沿用已有边界 |

依赖方向为：原生窗口/托盘/前端 → desktop 或 lifecycle；启动恢复 → CoreService；CoreService → SettingsStore 与 RuntimeService；登录项适配 → 操作系统。桌面呈现不能读写 Child，RuntimeService 不读窗口或登录偏好，维护下载回调不发起自动运行。

托盘由原生后台拥有，每秒读取一次不含日志的紧凑快照，仅在投影变化时到主线程修改菜单、提示和图标。不通过前端定时器维持托盘，不新增事件总线，不因这个投影频率增加更新网络检查或包校验频率。

托盘图标使用少量内置运行/停止/异常资源，核对高 DPI 和 macOS 单色模板；状态始终有文字，不只依赖颜色。资源进入正常应用包，不从用户机器或网络临时取图。

## 4. 设置迁移与持久化边界

schema 3 只增加以下字段，其余核心、更新和线路数据保持现有结构：

```json
{
  "startup": {
    "restoreCoreOnLaunch": false,
    "resumeCore": false
  },
  "desktop": {
    "backgroundNoticeShown": false
  }
}
```

restoreCoreOnLaunch 是用户开关；resumeCore 表示最后确认的恢复意图，不是实时 PID。backgroundNoticeShown 只记录首次收起说明是否完成，不引入关闭行为枚举。登录项状态不进入这份 JSON。

- schema 0/1/2 经明确迁移进入 3；新字段均为 false，不能由配置存在、核心已安装或旧 trial 推断曾经运行。保留来源、配置、自动更新开关和受管恢复记录。
- 升级前备份原 schema 文件，已有备份不覆盖；迁移幂等，失败保留原件。未知/损坏设置继续阻止写入和自动运行。
- 保留 SettingsStore 唯一 writer。新增字段级写入方法，从最新值合并；运行意图和提示记录不增加 preferencesRevision，也不因它们变化使网络设置草稿冲突。
- 启动恢复开关立即保存，不复用整份 UpdatePreferences 的草稿提交；两个独立设置入口不能互相覆盖。
- 启动成功记录与 trial 确认尽可能在同一串行提交完成；提交内复核核心上下文、操作取消和意图代次。确实改变核心恢复字段时沿用核心修订检查，单纯写运行意图不制造配置变化。
- 不另存 PID、程序副本、配置正文、上次窗口页面或完整状态历史；不靠退出时补写“刚才是否运行”来记忆。

## 5. 所有启停经过同一用例

将 CoreService 的 start_owned 整理为“本地采用/配置预检 → 一次启动和可选一次回退 → 统一成功确认”三个具体步骤，消除回退分支提前 return 而绕过记录的可能。页面、托盘和启动恢复共用该用例；外部核心成功启动也要记录意图。底层 RuntimeService 继续只管理进程。

| 事件 | 对恢复意图的影响 |
| --- | --- |
| 任意入口启动，含回退后成功 | 完成现有 2 秒观察和恢复记录确认后保存 resumeCore=true |
| 启动失败、确认前取消 | 不把失败写成成功，不将此前成功记忆伪造为当前运行 |
| 用户主动停止，含等待核心准备时 | 立即撤销本次恢复资格，保存 resumeCore=false，取消启动所有者并等待真实清理 |
| 退出、应用更新、Drop 清理 | 使用内部停止路径，不写 resumeCore=false |
| 运行中意外退出 | 保留恢复意图，报告实际失败；本次会话不自动再启动 |

启动确认/记忆写入失败沿用现有确认失败原则：停止本次新进程并报告；若停止失败则保留真实 PID/资源状态，禁止继续回退或创建第二个核心，不假称启动完成。

用户停止即使遇到磁盘失败，也必须继续尝试停止进程；返回“实际停止结果＋恢复状态保存失败”，并在本次会话抑制自动运行。若旧意图仍在磁盘，明确提示下次启动仍可能恢复，不能把失败说成保存成功。

移除 Stop 借用 Diagnostic 的做法：提供单个明确的停止票据。它可以取消正在启动的 Runtime 操作并等待其释放，但只有原所有者回收 Child；不得与网络诊断互相占位，也不得并发执行第二套 stop worker。重复停止合并或返回处理中。

CoreService 保留一个内存意图代次，用于拒绝旧启动结果覆盖新停止。主动启动、停止或更换配置/来源使尚未执行的旧恢复请求失效；选配置本身不触发启动。关闭恢复开关只取消恢复来源的待执行/正在启动操作，不能误取消用户手动启动；已确认运行的核心保持运行。

## 6. 一次性启动恢复与后台维护衔接

启动上下文只描述本次来源：手动、登录启动、更新重启、隔离验收。登录来源不保存在设置里；更新重启及手动唤出优先于登录收起，普通更新重启显示正常窗口，沿用 SoDeck 的规则。

启动顺序：

1. 解析参数及原生登录事件；在设置读取、迁移和 Application 初始化前完成实例接纳。
2. 主实例读取设置，建立后台返回入口，再根据来源决定显示或收起；用户激活请求到达时改为显示。
3. CoreService 执行本地恢复，返回结构化的自动运行安全结论；不等待前端挂载。
4. 当 restoreCoreOnLaunch 与 resumeCore 都为 true 且无安全阻断时，建立本次唯一恢复请求。
5. 已有可用核心立即走普通启动用例，不等待发行网络或应用更新缓存验签；必需核心缺失时复用现有准备/修复并等待其结果。
6. 核心准备收尾后由 Application 的 wake 唤醒恢复判断；启动前再检查开关、来源/配置上下文、请求代次、关闭状态和资源空闲，成功或失败后消费该请求。

恢复只需要有限的会话状态：无请求、等待必需核心、正在启动、已结束；结果附原因即可。不持久化一条待执行命令，不把“想运行”变成每分钟追赶目标状态的守护循环。

- 初始化发现未确认的 trial=starting、无法确认清理、损坏设置等情况，本次暂停自动运行并要求明确处理；不能因为新功能开启而绕过 v0.3.0 的恢复保护，也不能重试已阻断候选。
- 无配置、外部核心路径失效、配置不兼容、必需核心本次准备失败，均结束本次自动启动并显示原因。后台维护以后重试成功不复活这条已结束请求。
- 用户在等待期间停止、关闭恢复开关、更换选择或退出时，撤销待执行请求；下载完成、迟到回调或旧唤醒不能再启动。
- 用户手动启动接管本次请求；用户主动停止后，即使没有 PID，也要能点击停止取消“正在等待核心”的状态。
- 普通核心更新继续运行中不切换、不打断；自动恢复不另建下载器或版本选择规则。已有一次回退只算同一启动用例的一部分。
- 将 bootstrap、恢复用例和登录项修改纳入有所有者的退出等待。维护循环的 60 秒到期判断和现有 wake 保留，不改成每秒联网，不依赖页面刷新驱动自动恢复。
- 隔离 smoke 默认不登记登录项、不恢复真实代理；原生验收通过明确模式与固定夹具验证恢复，不把测试数据目录或参数传播到正常重启。

## 7. 收起、草稿与真正退出

窗口 CloseRequested 只请求 desktop 收起，不能封闭 Admission、停止核心、弹草稿决定或把窗口销毁。首次收起前复用现有原生 dialog 提供一次说明，取消保留窗口；确认且实际收起成功后才记录，不增加常驻配置选项。登录后台启动不触发这份首次关闭说明。系统文件框或退出决策处于实际存续期时暂不收起，显示对应窗口；dialog_open 的生命周期保留到原生回调结束，不因取消请求提前解除。

真正退出统一使用强类型目标 Quit / InstallAndRestart，替换现有 restart、install 两个布尔组合；删掉 Admission::close 中无效的 install 参数。托盘退出、Cmd+Q、ExitRequested、页面退出和更新按钮最终进入同一入口。

只增加与本产品匹配的退出阶段：空闲、等待草稿决定、收尾、已交接。只允许一个待决请求，携带请求 ID 和当前前端文档标识，避免重复点击、旧文档回执或迟到确认结束新会话。

- 收起不处理草稿。真正退出时向已就绪前端发起预检，干净草稿直接确认，有修改则复用现有保存/放弃/取消对话框。
- dirty 布尔只作为提示，不能作为唯一安全依据。前端就绪和 pending 请求有快照，事件只负责唤醒；托盘先点设置、先点退出或页面重载不能丢失请求。
- 未得到前端预检回执时不擅自丢草稿；机器回执等待有界，失败恢复可见窗口并反馈。用户已经进入保存/放弃决定后不设置强制替用户决定的超时。前端尚未就绪且没有本会话草稿时，允许原生直接走清理。
- 当前设置草稿的保存、放弃和判断仍由 updates.ts 持有；退出桥接只调用它，不复制第二份草稿模型。用户确认后锁住本次编辑/提交，取消或失败时恢复。
- 清理失败、安装失败或决定无法显示时恢复可达窗口并保留实际错误；不能仅向隐藏页面发 shutdown-error。
- 系统退出请求不能转为隐藏。运行意图在成功启停时已保存，不依赖关机回调完成记忆；系统强制结束时不承诺保存尚未提交的表单，Unix 强杀清理限制保留。

原生呈现顺序统一：恢复 macOS 普通应用身份、取消最小化、显示窗口并按明确用户操作聚焦；后台检查、普通日志和核心下载进度不调用显示。菜单“设置”导航保留为最新待导航目标，前端挂载后消费，不增加多窗口导航协议。

## 8. 单实例、登录来源与更新交接

把现有 instance.lock 抽为 instance::Lease，并让 SettingsStore 继续持有同一 Lease。生产路径提前接纳；测试的 open(root) 也调用同一获取逻辑。不允许“先运行再检查已有实例”，不删除锁文件绕过占用。

- 激活范围限定当前用户与规范化数据目录；端点名由用户身份和目录摘要导出，标识全部改为 sing-shell，不能触碰 SoDeck 的锁、端点或登录项。
- Windows 使用当前用户限定、拒绝远程客户端的命名管道并核对服务端身份；Unix 使用用户私有目录的 socket 和同 UID 校验。请求只允许固定版本的“显示主窗口”，限制长度和等待时间，不传文件路径、Shell 或通用 RPC。
- 主实例持有 Lease 后才创建/清理自身激活端点；端点尚未建立时有界重试。普通第二实例显示后退出，重复登录请求不打扰现有窗口。
- 激活只显示现有实例，不取消正在清理的退出。已交接时返回正在退出/重启；旧客户端没有激活能力时保留独占并给出原因，不强杀旧进程。
- 更新启动在有限时间内等待旧进程释放 Lease；保留数据锁到真实退出，不因“准备重启”提前放开。激活失败不能初始化第二套核心。

统一为 Tauri 提供归一化 Env：移除已消费的登录/旧重启来源，追加一次性本次替换信息；Windows updater 的安装后重启参数和 macOS/Linux request_restart 使用同一来源。新版本执行完后不得继续携带 --login-start，不能修改系统登录项来解决重启来源问题。

macOS 主应用登录项没有普通 --login-start 参数时，在 Tauri setup 的原生启动回调中读取一次登录 Apple Event，不能延迟到异步后台里再猜；手动 Reopen/Dock 激活也转为显示现有窗口。后台身份在首次呈现前确定，避免窗口先闪出再隐藏。

真正退出的顺序固定为：草稿决定 → 封闭接纳并取消恢复/维护 → 等待初始化、核心操作、下载和登录项写入 → 验证应用待装包 → 内部停止核心并确认 reader/检查进程收尾 → 完成必要原生交接准备 → 调用安装器或退出。

Windows 安装器可能直接结束进程，任何必须完成的工作不得位于 install 之后或依赖 Drop。插件 on_before_exit 最多做幂等标记，不承担可失败清理。ShellExecute/安装失败则撤销尚未生效的交接状态、重新开放可用入口；已经停止的核心保持真实停止，不为了“恢复退出失败前状态”暗中再启动。

## 9. 登录项的平台适配、依赖与安装器

登录项由系统作为唯一事实源；返回 enabled / disabled / blocked / stale / unavailable / unknown 和原因。未知或读取失败不能画成可靠的关闭状态。进入设置、应用重新获得焦点、修改完成后刷新，不在 700ms 轮询或每次启动时重新登记。

设置修改异步执行、单项串行、处理期间禁用重复操作；失败读回实际状态并就地显示。开启或关闭不隐藏当前窗口、不停止核心。退出必须等待已进入的系统修改完成；已进入不可撤销的系统操作不以取消信号冒充完成。

| 平台 | 方案及安装边界 |
| --- | --- |
| Windows 两架构 | 当前用户 Run 项，正确引用正式安装路径和登录参数；读取系统禁用事实，不修改 StartupApproved 以绕过用户关闭；所有用户安装也只修改当前用户 |
| Linux 两架构 | 当前用户 XDG autostart，处理路径转义、归属、Hidden/GNOME 禁用标记；DEB 使用稳定安装位置，AppImage 登记外层 APPIMAGE，不登记临时挂载内程序 |
| macOS ARM64 | 沿用 SoDeck 主应用登录项方案：13+ 使用 SMAppService.mainApp；现有最低系统范围需要时才保留 11/12 的私有 LaunchAgent 兼容路径，RunAtLoad 且无 KeepAlive；不静默提高最低系统版本 |

macOS 必须核对完整 Sing Shell.app 的标识、程序与图标资源，拒绝只读 DMG、临时目录和 App Translocation。Sing Shell 没有既往登录项，不照搬 SoDeck 的旧项迁移、旧任务探测及补偿流程。

新 `installer-hooks.nsh` 只在 Windows 标准卸载时删除当前用户中确实指向本安装位置的 sing-shell Run 值；/UPDATE 原样保留，包括被系统禁用的项目。不清理其他用户、其他安装副本或 SoDeck。macOS/appimage 直接删除缺少可靠卸载回调，正式说明中提示先关闭自启；不新增后台卸载服务。

依赖方案明确限制为：启用现有 Tauri 的 tray-icon；扩展现有 windows-sys 的 Registry/Pipes/必要安全与窗口 feature；本地激活按需启用现有 Tokio 的 net/io-util，用现有取消原语，不新增 tokio-util、single-instance、autostart、notification 插件。

macOS 原生登录 API 是唯一提出的新增直接生产依赖范围：建议将锁文件中已由 Tauri 使用的 objc2 0.6.5 与 objc2-foundation 0.3.2 声明为 macOS 限定直接依赖，使用必要的 Foundation feature。理由是复用已有绑定与 SoDeck 已有适配，避免自行手写 Objective-C 消息 ABI；替代方案是仅用 LaunchAgent，会失去现代主应用登录项的系统身份和状态语义。AGENTS 约定未经明确要求不新增生产依赖，因此本段是明确列出的选型建议，本轮不引入；后续采用本方案实施时只限这一范围，不顺带增加 AppKit 包装库或通用平台框架。最低系统、API 可用性与包内实际链接均需验证。

## 10. IPC 与前端配套

保留 core_action 作为启停入口，增加操作来源由后端决定，前端不能伪造 Restore 来绕过限制。内部停止不暴露成用户按钮。

新增或调整的 IPC 只服务真实动作：

- 桌面快照与 frontend_ready：实际可见性、返回入口可用性、待导航、退出请求和桌面错误；回执核对请求和文档标识。
- 登录项 read/set：返回系统事实和原因；独立于更新偏好保存。
- 恢复开关 set：字段级立即保存；只撤销恢复来源的待执行请求，不影响已确认运行。
- 统一退出 request/decision：保留用户可理解的退出和更新动作，内部使用强类型目标；旧的双布尔入口移除。
- 核心快照增加本次恢复等待/结果和操作可用事实；停止按钮在等待自动恢复时也可用。

紧凑运行投影统一用于托盘和页面：实际运行/正在停止优先于维护错误，已有核心运行时不能因更新失败显示成核心已停止。cleanup_pending、启动/停止处理中和恢复待执行均进入操作可用判断；不由两个界面各猜一套。错误分别归属核心运行、核心维护、应用更新、登录项和桌面呈现。

新增小型 `desktop.ts` / `startup-settings.ts` 负责原生桥接和两个立即生效的开关；main.ts 保留装配和两页导航。updates.ts 保留现有更新、网络草稿和保存能力，提取其退出预检供统一桥接调用；不重建整个 UI 或加入框架。

调用者配套包括 src/core.ts 的 Settings/RuntimeSnapshot/IPC 类型（补齐 cleanupPending）、core-model/core-status 与 runtime.ts 的状态和操作按钮、index.html 的两页及草稿文案、lib.rs 的模块出口、Cargo feature/锁文件、Tauri 初始窗口和 NSIS hook 配置。Rust 测试 support、固定设置样本与脚本 schema 断言一起迁移；Rust 端拥有原生能力，capabilities 不扩大成任意系统操作权限。

页面文案同步移除“关闭窗口会停止核心”“更新重启后一律手动启动”等旧承诺。动态说明恢复开关、实际失败和系统禁用，不把开机自启写成登录前服务。保留网络草稿、日志文本/滚动、详情展开和输入焦点；设置失败不重置其他表单。不扩大前端权限为任意注册表、文件或命令访问。
