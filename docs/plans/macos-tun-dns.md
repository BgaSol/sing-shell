# macOS TUN DNS 功能设计

状态：设计定稿，尚未实现、尚未实机验证。日期：2026-11-26。

## 目标与结论

用户选择节点并连接后，使用 macOS 系统解析器的应用应通过 TUN 获取符合分流规则的域名结果；断开后回到系统原有解析行为。无需手动修改 Wi-Fi DNS，也不新增 DNS 开关、设置页或额外授权步骤。

137 Mac 的故障已定位到系统 DNS 接管缺失：同一 VLESS 节点通过独立代理可以访问，现有 TUN 也能转发正确目标地址，但系统仍向物理接口上的局域网路由器查询，得到错误地址。局域网直连使这些 DNS 请求绕过 TUN，核心的 `hijack-dns` 看不到请求。该复现不能归因于 VLESS 导入或节点协议不兼容。

采用**由现有按需授权 worker 持有临时系统解析器**的方案。继续使用独立官方 sing-box，壳只补齐系统 DNS 的登记、确认与释放。

| 方案 | 本次选择的依据 |
| --- | --- |
| 临时 SystemConfiguration 解析器 | 采用。随 worker 会话存在，不修改已有网络服务的持久 DNS 偏好，不需要恢复备份。 |
| 改写 Wi-Fi／以太网 DNS | 不采用。需要持久备份、切网协调、冲突判断和崩溃恢复，增加状态与维护成本。 |
| Network Extension | 不采用。涉及签名发行、扩展和核心平台接口迁移，超出本问题所需范围。 |

## 用户行为

1. **连接**：沿用当前连接按钮和系统管理员授权，依次准备核心、建立 TUN、接管 DNS。全部确认后才显示“已连接”，托盘使用同一状态。
2. **连接失败或取消**：清理本次 DNS、核心和 TUN，保留节点与有效设置；失败原因显示在现有错误区域，用户可重新连接。
3. **断开、退出、应用并重启**：先撤销本次 DNS，再结束核心并等待接口释放。应用更改复用现有流程，清理完成后才能创建下一次 DNS 会话。
4. **异常退出**：核心退出或控制端失联进入同一清理流程；不自动重连，也不自动再次弹出授权。worker 被强杀时，临时 DNS 依靠系统会话回收，核心残留仍按现有受保护进程记录处理。

不增加“修复 DNS”按钮或让用户选择 DNS 接管方式。出现问题应明确报错，不能静默退回会重现本次故障的半连接状态。

“已连接”表示本机核心、TUN 和系统 DNS 接管就绪，不保证远端节点或任意网站可达。每次连接不依赖 Google、Cloudflare 或其他固定外网探测成功；真实域名请求用于验收，不作为产品连接门槛。

## DNS 行为与边界

- **系统入口**：为普通系统域名查询登记默认临时解析器，服务器指向本次 TUN 的 DNS 地址。IPv4、IPv6 地址与生成配置共用同一份内部定义，避免两边不一致。
- **核心职责**：继续使用真实 IP、现有域名／站点分流及 `hijack-dns`。代理 DNS 继续经节点访问现有 HTTPS 上游；直连域名和节点主机名继续使用官方核心的物理网络本地解析能力。代理 DNS 失败不新增本地 DNS 回退。
- **节点解析防回环**：沿用官方核心 `local` 解析，不在壳里实现 DNS 客户端。接管前后必须确认当前物理接口存在核心可以独立选择的 scoped 上游，且不是本次隧道 DNS；IPv6 链路本地地址的接口作用域必须保留。缺少这种独立入口时停止连接，不能让核心回退到刚安装的默认隧道解析器。
- **局域网**：保持局域网流量直连。普通私有域名服从现有 DNS 分流规则；`.local`、系统搜索域和更具体的系统域名解析范围继续遵循 macOS 行为，本次不扩展为企业分域 DNS 管理器。
- **网络变化**：临时解析器始终指向当前 TUN，不跟随 Wi-Fi 名称改写网络偏好。复用 worker 运行循环低频复核本地网络条件；切网后物理上游仍独立可用则继续，由核心处理网络适配；无法确认安全上游或自己的 DNS 接管失效则清理并提示重新连接，不自动重连或反复争抢 DNS。
- **适用范围**：仅 macOS 节点模式的受控 TUN。原始配置及外部核心继续由用户配置决定；Windows、Linux 保持现有行为。浏览器自带 DoH、主动指定 DNS 和其他 VPN 的优先级冲突，不承诺全部接管。

## 一次连接的完整生命周期

### 建立

1. 获得现有机器级租约，完成受保护残留恢复，确认没有另一套受控 TUN。
2. 读取物理网络及其独立 DNS 入口；此时尚未登记本次解析器。生成配置、校验并启动官方核心。
3. 确认真实核心 PID、TUN 接口、双栈地址和路由就绪。
4. 创建专属于本次连接的 `SCDynamicStore` 会话，以随机独立服务键登记临时 DNS：
   - 键：`State:/Network/Service/sing-shell-<随机值>/DNS`。
   - `ServerAddresses`：当前隧道的 IPv4／IPv6 DNS 地址。
   - `SupplementalMatchDomains`：`[""]`，覆盖普通默认域名查询。
   - `SupplementalMatchOrders`：`[1]`，优先于普通默认解析器；不覆盖更具体的系统域名范围。
   - 只使用 `SCDynamicStoreAddTemporaryValue`，不写 `Setup:` 或已有服务的 DNS 键。
5. 读回本次键和值，确认 macOS 有效解析器视图包含本次默认解析器，并复核物理上游仍可独立选择。动态存储写入成功本身不足以宣布接管成功。
6. 刷新本机 DNS 缓存，避免沿用连接前的污染结果。刷新使用固定系统接口／程序参数，不接受节点或用户输入形成命令；失败按启动失败处理。
7. 最后再次检查取消标记、核心存活和资源归属，发布 `Running`。复用现有网络就绪时限与取消机制，不增加无限重试或外网探测等待。

### 释放

1. 取消并等待启动任务结束，避免断开后迟到登记 DNS。
2. 释放本次临时解析器，确认自己的键消失，并刷新缓存；此时核心仍在，减少清理中的无效 DNS 窗口。
3. 停止核心，执行现有残留恢复，确认真实接口和进程资源释放。
4. 所有本次资源确认释放后才显示已断开、撤销所有者并允许新连接或安装更新。

启动失败、用户取消、核心异常、控制端失联和正常断开使用同一份释放逻辑。某一步失败仍尽力释放其他资源，保留原始失败与清理原因；任何本次资源未确认释放都保留 `CleanupRequired` 和实际所有者，不假报断开。

临时值由持有它的系统会话回收，不能只依赖 Rust 的 `Drop`：必须实测 worker `SIGKILL` 后的系统行为。Apple 的自动删除保证以该键未被其他会话更新为前提。本程序不通过第二个会话改写该键，不扫描删除其他应用的 DNS，不把相同前缀当成可删除依据。

worker 被强杀后“临时 DNS 消失”与“核心／TUN 全部释放”分别验收；不把前者当作整套网络已恢复的证据，不为此增加持久后台服务。

## 状态与错误

复用 `Preparing / Starting / Running / Stopping / Failed / CleanupRequired`，DNS 是 `Starting` 的必要完成条件，不增加并行状态机。前端与托盘继续只依据统一阶段判断连接状态，不增加持久设置或设置 schema 迁移。

错误放在现有网络失败类别，区分原因并给出明确下一步：

| 情况 | 用户提示方向 |
| --- | --- |
| 临时 DNS 登记或确认失败 | “未能接管系统 DNS，连接已停止。请重试；若同时运行其他 VPN，请先断开。” |
| 缺少独立物理 DNS 入口 | “当前网络没有可安全使用的本地 DNS，连接已停止。请检查网络后重试。” |
| 切网后接管条件失效 | “网络或 DNS 设置已变化，连接已停止，请重新连接。” |
| 清理未完成 | “网络清理未完成，请重试停止。”保留实际未释放的资源信息。 |

壳新增日志只记录阶段、系统调用错误与脱敏的本机资源状态，不增加查询域名、节点凭据或完整配置的记录；核心日志保持现有有界、脱敏和本地展示规则。不得将节点不可达、DNS 上游失败一概归为授权失败。

## 代码范围与复杂度控制

| 位置 | 预期改动 |
| --- | --- |
| `src-tauri/src/platform/` | 新增 macOS 专用 DNS 资源所有者，负责临时会话、读回、有效解析器／物理入口检查、缓存刷新及释放。直接绑定系统 Framework，复用已有 FFI 风格，不新增生产依赖。 |
| `src-tauri/src/session/tunnel/worker.rs` | 把 DNS 资源纳入当前启动、运行检查和统一停止；启动线程结束后仍由 worker 持有，避免局部变量提前释放。保留取消、超时和所有者规则。 |
| `src-tauri/src/profile/config.rs` | 将隧道 DNS 地址收敛为现有生成配置和平台适配共用的内部常量；不新增用户参数，不改变协议配置语义。 |
| 测试及现有网络夹具 | 增加生命周期失败注入与真实系统解析验证；更新原有“接口就绪即成功”的验收假设。 |
| 正式文档 | 实现后更新核心、分流和架构合同；将本计划的最终行为迁入正式文档并删除本计划，导航只改文档索引。 |

不新增通用网络资源框架、常驻 DNS 代理、自动修复守护、测速、Fake-IP、持久 DNS 备份或第二套配置引擎。若运行快照无需新增字段即可表达统一连接阶段，就保持现有 IPC 结构。

## 实施顺序与验收

先在 137 Mac 用隔离临时会话验证系统 API、官方核心及节点解析的组合，再接入产品。该验证必须覆盖默认解析器确实生效、物理 scoped 上游仍独立、会话正常关闭及强杀后临时值消失。任一项不成立，都不能直接集成并发布；本方案不静默降级为持久修改 DNS。

集成后，以下行为全部通过才算完成：

| 场景 | 验收标准 |
| --- | --- |
| 原故障网络 | 在路由器 IPv4／IPv6 DNS 产生错误结果的环境，用系统 `getaddrinfo`／`dns-sd` 和普通应用请求验证：代理域名查询进入核心，得到正确结果并经同一 VLESS 节点访问。不能仅凭 `dig @隧道地址` 或 `curl --resolve` 宣布修复。 |
| DNS 与分流 | 覆盖 A、AAAA、DNS UDP／TCP、域名形式节点的冷启动、代理／直连规则、私有域名、搜索域及 `.local`。节点解析无回环；代理 DNS 失败不会新增向路由器的回退。 |
| 本机就绪与远端失败 | 有效接管但节点不可达时，不误报系统授权失败；不因固定探测网站不可达拒绝本机连接。缺少独立物理 DNS 时明确停止，不留下解析器。 |
| 失败及取消 | 注入核心启动失败、登记失败、读回失败、缓存刷新失败、登记后的取消；清理成功后无本次键、核心或接口残留。清理失败保留 `CleanupRequired`，迟到启动不能恢复运行。 |
| 正常结束 | 断开、退出、应用并重启、连续连接均无重复解析器；手动 DNS、自动／DHCP DNS 的持久偏好前后相同，未改写无关网络服务。 |
| 异常结束 | 分别终止核心、控制端及 worker；核实临时键回收、系统解析恢复和既有核心残留恢复，分别记录完成时间与未释放资源。 |
| 网络变化与冲突 | Wi-Fi／以太网切换、IPv6 链路本地 DNS、无 scoped 上游、同时运行另一 VPN。安全条件成立则保持连接；条件失效则清理并提示，不覆盖其他软件的键或反复抢优先级。 |
| 平台及发行回归 | macOS ARM64 用实际应用包完成系统授权、系统解析和退出验收；Windows x64／ARM64、Linux x64／ARM64 完成现有包与网络回归。保持当前五原生发行目标，只记录实际执行结果，跳过项单列。 |

测试不依赖维护者的生产节点或固定公网域名；自动化优先使用可丢弃环境中的受控 DNS／节点，用户实机复现作为补充。普通单元测试不提权、不修改宿主网络。实现时运行相关 `npm run check`、`npm run scripts:test`、`npm run test`、`npm run build`；新增回归验证要能在旧逻辑下暴露系统解析入口缺失。

## 依据与待验证风险

- [官方 Apple 客户端在隧道设置中配置 DNS](https://github.com/SagerNet/sing-box-for-apple/blob/faecb366731c19d189c888e1044840d4fa1352df/Library/Network/ExtensionPlatformInterface.swift#L42-L184)，说明系统解析入口需要平台层接入。
- [当前官方独立 Darwin TUN 路径](https://github.com/SagerNet/sing-tun/blob/040db71fcd33196f1d15708b91eb61e9dc6ab8dd/tun_darwin.go#L152-L173) 未提供本方案的系统 DNS 登记，不能仅依赖 `dns_mode=hijack`。
- [临时 SystemConfiguration 解析器的公开实现](https://github.com/MetaCubeX/sing-tun/blob/e454d9c11e5a41ee348dd22fda93e9bb441ea2d8/internal/systemconfiguration/dns.go#L187-L260) 提供具体系统 API 和字典用法；本项目复用思路，不替换官方核心。
- [Apple 临时值的会话回收契约](https://developer.apple.com/documentation/systemconfiguration/scdynamicstoreaddtemporaryvalue(_:_:_:)) 是免持久恢复的依据，强杀、缓存和多解析器优先级仍需实际包验证。

最大未验证项是该临时解析器与当前官方核心 `local` 解析在不同物理网络下的组合行为。设计已确定使用这条路径，并以无回环、系统解析生效和退出回收作为上线门槛；当前不能声称 VLESS 故障已修复。
